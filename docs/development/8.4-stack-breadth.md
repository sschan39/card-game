## Proposed announcement structure

Keep a serializable announcement record containing chosen modes/part, X values, target-group cardinalities, divisions and selected cost route. Derive one effective cost before payment, then lock the announcement on the stack. Resolution reads the locked values instead of recalculating X from the current mana pool or source state.

```text
Live access/timing query
  → choose modes, variables and cost route
  → derive complete effective cost and target schema
  → choose targets/divisions/payment
  → validate and plan all costs
  → atomic commit and stack insertion
  → ordinary whole-object revalidation/resolution
```

Alternative costs replace the relevant base cost; additional costs compose with the selected route. Do not encode every route as a separate player action. Cost expressions and target counts share announced variables, with bounded integer validation before any costs are committed.

## Stack-copy boundary

Copy planning consumes an existing stack object and any permitted choice changes. It creates a new stack identity carrying locked announcement values and independent target references. It does not announce a new cast, replay paid costs or automatically emit a cast event. Exact copy restrictions must be modeled explicitly. The structural destination of a resolving copied permanent spell requires the creation contract in 8.3; spell-copy lifecycle must be specified before implementation.

## Stop conditions

Stop if X requires reading arbitrary card-name fields, alternative costs bypass shared planning, a copy is faked as a normal cast, or required announcement state is stored only in a closure/client UI. Define the general serialized contract first.
