# 8.2 slice — Generic attachment operations

Status: proposed for owner review; no implementation. Source baseline `242861a`, inspected 12 October 2026. Parent: [attachments](8.2-attachments.md).

## Missing behavior and purpose

The room already stores an attachment's host UUID/revision or player ID. State-based actions remove illegal Auras and detach illegal Equipment/Fortifications. `UNATTACH_CARD` and its delta mapping exist. There is no corresponding attach operation or generic effect, so these checks currently consume attachment state established only by fixtures.

Example: a generic activated ability resolves with a creature as its chosen host. The engine already handles ability costs, the stack and target revalidation, but has no ordinary instruction to bind the source Equipment to that host. A typed attach operation supplies that missing step. If the host departed and returned, its old reference fails; no direct fixture write or named-card branch is needed.

This slice establishes and changes bindings between existing battlefield objects, or from an Aura to a player. It does not implement Aura spell entry, equip-specific costs/timing, new cards, zone browsers or effects granted to an attached host.

## Alternatives

1. **Shared legality plus typed operations — recommended.** One query serves planning, reduction and state-based cleanup. Generic effects use the existing resolution path; events and deltas describe actual binding changes.
2. **Add an effect that writes attachment fields.** Duplicates legality or relies on a later checkpoint to repair an invalid binding. It also bypasses the established mutation/outcome boundary.
3. **Implement the complete Aura/equip workflow first.** Includes entry replacements, announcement targets and characteristic recipient scopes before a reusable binding operation exists. Keep those as subsequent independently reviewable slices.

## Types and responsibilities

Add `src/types/attachment.types.ts`:

```typescript
interface AttachmentReference { cardUuid: string; zoneRevision: number }
type AttachmentHost =
  | { kind: 'card'; cardUuid: string; zoneRevision: number }
  | { kind: 'player'; playerId: string };
type AttachmentHostState =
  | { kind: 'card'; cardUuid: string; zoneRevision?: number }
  | { kind: 'player'; playerId: string };
```

Add `ATTACH_CARD` to `GameMutation` with `{ attachment: AttachmentReference; host: AttachmentHost }`. Extend the existing `UNATTACH_CARD` with optional `zoneRevision` for compatibility; new engine-produced requests carry the exact revision. No room-owned attachment registry, record ID or configuration setting is needed: the existing card state remains authoritative.

Create `src/engine/attachment-service.ts` with:

- `attachmentHost(card): AttachmentHostState | undefined`: reads existing state without inventing a missing host revision. Mixed card/player host fields are invalid, not a choice of whichever field happens to be checked first. Missing revisions in legacy fixture state retain the current ongoing-cleanup behavior; new requests require exact revisions.
- `attachmentLegal(room, attachment, host: AttachmentHostState): boolean`: shared ongoing legality, using effective characteristics, structural requirements and protection. It never applies shroud/hexproof or other target-only restrictions. The planner/reducer require the stricter `AttachmentHost` request shape before calling this query.
- `planAttachment(room, attachmentRef, host): GameMutation[]`: validates both exact references and legality, returning one attach instruction or none.
- `applyAttachment(room, mutation): OperationOutcome`: repeats validation against live state; establishes one host and clears incompatible fields atomically. Invalid requests reject; the same exact binding is unchanged. A new binding commits.

The source attachment and card host must be live battlefield cards, with matching nonnegative safe-integer revisions. Self-attachment fails. The attachment must have an effective Aura/Equipment/Fortification subtype and must not currently be a Creature or Battle, matching the existing cleanup boundary.

Equipment hosts require effective Creature type; Fortification hosts require effective Land type; player hosts are supported only for Auras and require a current room player. Card-host Auras use authored `attachmentRequirements` when present. Apply any authored requirements to Equipment/Fortification as well, in addition to their default host type. The current private check returns early for those categories and ignores such restrictions; sharing the query removes that inconsistency structurally.

Reuse `structuralTargetLegal` for authored host restrictions and `protectionApplies` for card-host protection. Preserve the current controller-relative interpretation of requirements. Do not add an implicit "host must be controlled by the attachment's controller" rule: a specific ability's targeting definition owns that restriction.

Successful attachment updates only the existing host fields. It preserves UUID, zone revision, controller, counters, damage and orientation. Immutable reducer copies are ordinary state updates, not creation of a new card instance. An invalid change keeps the original binding intact rather than detaching first.

## Generic effects and normal flow

Add `ATTACH` to `EffectRegistry`. Its attachment is the resolving stack object's source, bound by that source's exact battlefield incarnation. It accepts exactly one revalidated card/permanent/player host pointer and uses `planAttachment`. Multiple hosts, malformed pointers, stale sources and illegal hosts produce no attach instruction. A departed source is not refreshed to its returned incarnation.

Add `UNATTACH` over existing revalidated card/permanent pointers, producing exact `UNATTACH_CARD` requests. Source-targeted definitions can use the existing `targeting.subject: 'source'` representation. No new player command is introduced. A synthetic generic activated ability is sufficient to verify this path through normal sockets; it is not a new playable named card.

```text
Existing activated ability announcement and costs
  → stack
  → existing target/source identity checks
  → generic ATTACH/UNATTACH effect
  → shared binding planner
  → reducer validates and commits host fields
  → actual lifecycle event and ordinary delta
  → existing state-based cleanup using the same legality query
```

This first slice cannot attach a still-resolving Aura spell by pretending its source is on the battlefield. Atomic Aura entry plus binding is a separate structural contract. It also does not implement equip as a direct player action that skips costs or the stack.

## Ongoing cleanup, events and deltas

Replace the SBA planner's private attachment check with the shared query, preserving Aura graveyard versus other-attachment detach behavior. New detach proposals carry the source revision. Missing/illegal hosts, changed effective types and protection continue to settle through the existing checkpoint loop.

Make `UNATTACH_CARD` reject an explicitly stale revision and preserve state for already-unattached objects. Existing legacy requests without a revision retain their current lookup behavior. Clear all three host fields together.

Add one `ATTACHMENT_CHANGED` event with `{ attachment: AttachmentReference, before: AttachmentHostState | null, after: AttachmentHostState | null }`. Creation, host change and removal are distinguishable without inventing an intermediate detached state. Derive it from actual per-step before/after stored bindings, including attachment zone departure/reset, so movement and ordinary attach/detach operations share the same lifecycle observation. A host departure is observed through the ordinary move event and subsequent checkpoint detachment; do not fabricate an earlier attachment-field write. Invalid mixed legacy fields do not represent a valid binding; their cleanup still emits the ordinary mutation/delta. Existing zone events remain present. The generic logger needs no special case.

Map `ATTACH_CARD` to the existing attachment card-state delta path. Keep `UNATTACH_CARD` and zone-move mappings on their ordinary paths. No independent attachment cache is synchronized. Recipient filtering and full debug snapshots keep their existing contracts.

## Characteristic boundary

`WHILE_ATTACHED` is currently an effect lifetime check using only `attachedTo`; it does not define who receives the effect. Extend its presence check to recognize either card or player attachment state. Do not call the effective attachment-legality query from characteristic-layer evaluation, which would recurse back into characteristics.

Existing resolved scopes remain frozen to their captured recipients. Moving an attachment must not silently rewrite those scopes. A dynamic "attached host" recipient selector, and the effects consumers that need it, require a separate characteristic-scope contract. This slice claims correct binding state and lifetime presence, not completed Equipment/Aura bonuses.

## Stop boundaries

Stop before named-card cases, fixture writes in production actions, target-validation bypasses, separate equip payment/stack code, a second authoritative attachment representation, compensating continuous-effect rewrites, or an Aura entry workaround after a checkpoint. The subsequent entry/recipient contracts must be designed before those consumers are implemented.
