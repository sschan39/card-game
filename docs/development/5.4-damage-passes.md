# 5.4 — Damage passes and response windows

Status: generic pass scheduling/participation implemented; First Strike and Double Strike consumers remain deferred. Inspected at `60e9349`, 12 October 2026. [Development index](README.md).

## Purpose and structure

Keep the engine open for more than one damage pass without building a particular keyword into phase progression.

| Module | Responsibility |
|---|---|
| `src/engine/combat-rules.ts` | `damagePasses` and `dealsDamage` hooks; default unique `normal` pass |
| `src/types/combat.types.ts` | Saved pass schedule/index/completion |
| `src/engine/combat-service.ts` | Start/restart planning with live participants for each pass |
| `src/engine/game-engine.ts` | After a completed pass, ordinary responses; next pass only after consecutive passes |

Pass IDs must be nonempty and unique. Each pass recomputes sources/recipients/current power after prior damage, SBAs, triggers and responses. Partial allocation and current pass position remain serializable room data. Nonpositive power creates no damage request.

## Flow

```text
Pass schedule → manual allocation → simultaneous damage → checkpoint → priority
 → two empty-stack passes → next damage pass against live board, or end combat
```

## Extension boundary and remaining work

The hooks and response windows are implemented; keyword strings do not automatically supply First/Double Strike semantics. A future consumer must define pass membership and characteristic-change behavior with dedicated scenarios. Owner authorization is required to resume deferred keyword consumers. No new settings are needed for current engine hooks.

## Acceptance evidence

`tests/engine/combat-choices.test.ts` uses synthetic registered passes to prove intervening responses, updated live participants and serialized pass restoration. `tests/engine/ordinary-turn.test.ts` proves ordinary combat windows. These tests establish extensibility, not keyword conformance.

## Stop condition

Stop if multiple passes are precomputed from one stale room or a deferred keyword is hardwired into `TURN_SEQUENCE`/combat loops.
