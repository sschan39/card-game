# 1.1 — Player command boundary

Status: Implemented command routing and lean debug modes.

Inspected source baseline: `ad6a96e`, 12 October 2026. [Development index](README.md). Source inspection documents current structure; test paths below identify verification responsibilities, not a new passing run.

## Purpose

Give player commands one authoritative route while retaining explicit development shortcuts.

## Current structure

- `src/server/action-packet.ts` — parseActionPacket validates the transport envelope.
- `src/server/reconnect.ts` — resolves stable player identity from socket mappings.
- `src/engine/player-commands.ts` — playerCommands descriptors and validateActionData.
- `src/engine/game-engine.ts` — executePlayerAction and pending-choice/terminal boundaries.
- `src/config.ts` — centralized debugMode.

The server resolves membership/identity and delegates the action. Descriptor-specific shape/status/debug requirements and engine priority/choice checks decide legality. resolve_stack and end_turn are explicit stack/flow debug facilities, not ordinary rules automation.

## Flow

```text
Socket envelope → stable identity/membership → descriptor validation → engine action → proposals/commit/checkpoint → sync
```

## Extension boundary

Add known player actions in src/types/action.ids.ts, descriptor routing, options and protocol together. Keep effect primitives extensible separately from player-action IDs.

## Remaining work and modification notes

Retain lean debug modes and full debug state. New actions use the same boundary rather than new socket authority paths.

## Acceptance evidence

- tests/server/action-packet.test.ts and tests/engine/player-commands.test.ts check malformed input/status/priority/choice ownership.
- tests/client/debug-controls.test.ts and tests/server/live-routing.test.ts cover debug visibility/routing.

## Stop condition

Stop if a new action directly mutates room state in server.ts, bypasses a pending decision or adds rights machinery unrelated to the requested engine behavior.
