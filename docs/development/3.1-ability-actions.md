# 3.1 — Activated ability actions

Status: implemented stable ability selection for supported battlefield activations. Inspected at `c651cda`, 12 October 2026. [Development index](README.md).

## Purpose and current structure

Select the authored ability, not an effect primitive. Two abilities using the same primitive must have separate costs, timing and identity.

| Module | Owns |
|---|---|
| `src/types/action.ids.ts` | `activate_ability` known action |
| `src/types/card.types.ts` | Activated ability definition and ID |
| `src/engine/handlers/activate-ability-handler.ts` | Pure definition lookup, validation and stack plan |
| `src/engine/card-characteristic-service.ts` | Effective abilities/control rather than printed-only lookup |
| `src/engine/option-service.ts` | Advertised ability ID and cost description |
| `src/engine/turn-history.ts` | Per-turn use identity/limits |

The packet selects `cardUuid`, `abilityId`, modes, target groups and cost choices. The engine supplies stack identity; effective server definitions supply costs/effects. The handler finds the controlled battlefield source, rejects mana abilities from this path, checks permission/timing/use limits, plans targets/divisions and shared costs, then creates an `ActivatedStackObject`. The source stays in its zone unless a paid cost moves it.

## Flow

```text
Advertised effective ability → missing announcement choices
 → validate selected definition and complete costs
 → commit costs + PUSH_STACK + use record → checkpoint → controller priority
 → ordinary stack resolution (source may already have departed)
```

## Extension boundary and remaining work

New activated rules belong in effective ability data and shared planning, not an action ID per primitive/card. Granted/removed abilities already use the same lookup. Loyalty costs remain unsupported and belong to 8.3. General activation access from nonbattlefield zones needs a shared access contract; current lookup is battlefield-only. Named-card additions remain outside the owner's engine-first scope.

## Acceptance evidence

`tests/engine/activate-ability.test.ts` covers same-primitive distinct IDs, definition authority, timing, modes and invalid selection. `tests/engine/action-costs.test.ts` and `tests/engine/source-information.test.ts` cover cost/source lifecycle. Current socket option/activation scenarios live in `tests/server/live-routing.test.ts`; effective-grant scenarios exercise dynamic abilities. Historical named fixtures are existing coverage, not authorization to build more card mechanics.

## Stop condition

Stop if an ability requires a card-name branch, client-provided cost/effect authority or a second activation orchestrator.
