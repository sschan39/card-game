# 8.4 review — Announcement and stack integration

Status: source review complete; new announcement/copy contracts not approved. Inspected baseline `21afb78`, 12 October 2026. Parent: [stack breadth](8.4-stack-breadth.md).

This audit records that source baseline. Since then, [Slice A shared numeric evaluation](8.4-numeric-values.md) has been implemented and verified for existing effect, condition and characteristic consumers. Declared announcement choices and stack bindings are still absent; the cost-route/copy gaps below remain open.

## Existing flow

```text
Effective definition and ordinary timing/access checks
  → choose modes
  → choose exact target groups
  → announce targeted distributions
  → choose nested mana activation costs, discard and payment
  → revalidate completed action and plan all costs
  → commit costs and insert stack object
  → whole-object legality and sequential resolution
  → actual events, checkpoint and ordinary sync/reconnect
```

`src/engine/action-choices.ts` stores the unfinished command in an `ActionContinuation` and reruns preparation after each answer. The spell and non-mana ability handlers reuse modes, target groups, distribution and cost planners. Their final stack effects contain selected mode effects, exact target references and flattened per-target distribution amounts. Modes and distributions therefore have real executable behavior even though the stack has no general announcement record.

The nine-entry catalog has no declared X cost, alternative/additional route or stack-copy effect. The gaps below concern extending the engine's contract; none establishes an urgent failure for a current catalog consumer.

## Source map

| Boundary | Existing contract | Required extension |
|---|---|---|
| Definition parsing | `src/library/card-parser.ts` accepts fixed numeric/colored mana symbols; `parseManaCost` rejects `{X}` | A typed authored variable and its cost expression, distinct from concrete mana payment |
| Numeric costs | `ManaCost` and `ActionCost` contain numeric resource amounts; `src/engine/mana-pool.ts` validates concrete nonnegative safe integers | Resolve announced expressions to valid concrete amounts before shared payment planning |
| Action payload | `src/engine/action-registry.ts` permits extra unknown fields | Explicit validation/ownership for declared variable values; an arbitrary extra packet field currently has no X semantics |

| Choice rendering | `ChoicePanel.tsx` offers selections or fixed-total allocations | Reuse this component, but define a scalar numeric choice contract; payment/distribution inputs cannot choose their own total |

| Command execution | `play-card-handler.ts` and `activate-ability-handler.ts` derive and validate the selected effects and costs | Consume the same validated announcement derivation as prompts, avoiding independently interpreted X values |

## Examples and cause of change

**X:** a synthetic spell costs `{X}{R}` and changes a player's life by `-X`. Its controller chooses X=3 and pays four mana. Later mana-pool changes must not change the effect's amount. Today the parser rejects `{X}`, and `DYNAMIC:source.power` is an unrelated live characteristic query. Extending only the parser would leave the announcement, concrete payment and locked amount missing.

**Variable targets/divisions:** an effect permits up to X targets and divides X among the chosen targets. Target counts and `choice.total` are currently fixed numbers. Substitution must precede `describeTargetGroups` and distribution validation; doing it only in the resolving effect would accept an announcement against the wrong target schema. Existing distribution rules require at least one per announced target, so X=0 needs a feasible zero-target definition rather than an impossible prompt.

**Cost route:** a synthetic spell offers its ordinary mana cost or another authored cost, and also requires discarding a card. The selected route determines the complete payable cost before the existing atomic planner runs. Encoding another action ID or paying the discard during resolution would fragment the shared action/payment contract.

**Copy:** copying a spell already on the stack creates another stack object with the same locked X/modes/divisions and independently bound targets. Reusing an ordinary spell object with the original physical source does not establish correct lifecycle: structural resolution and `COUNTER_STACK` currently move physical spell sources. A copy needs an explicit representation first. Copied permanent entry also depends on [8.3 creation](8.3-family-integration-review.md).

## Existing evidence and remaining acceptance

- `tests/engine/pending-choices.test.ts` covers modes before payment, target/discard prompts, announced divisions, infeasible prompts, cancellation and serialized resolution recovery. Those tests do not exercise a numeric announcement field.
- `tests/engine/target-groups.test.ts` covers group completeness, exact incarnation references and legality changes. Reuse those boundaries for resolved variable cardinalities; the broader targeting review remains separate.
- `tests/engine/action-costs.test.ts` covers combined payment, rollback, nested mana selections and cast-source reservation. Extend the same planner for derived costs rather than add a separate payment implementation.
- `tests/engine/countering.test.ts` covers physical spell and ability removal, paid-cost retention and source preservation for abilities. It does not establish copied-spell lifecycle.
- `tests/client/pending-choices.test.ts` exercises IDs and exact fixed-total allocation. Numeric announcement rendering/answering and recovery would need new cases in the same component.

This is source review, not a new test run or implementation-completion claim. Future acceptance must prove X=0, malformed/negative/fractional/unsafe values, cost-expression overflow, stale source rejection during prompts, fixed values after payment, feasible variable groups/divisions, serialization/reconnect and no partial payment. Copies additionally need independent identity, no extra cast/payment event, correct counter/removal and permanent versus nonpermanent destinations.

## Bounded implementation choices

1. **Shared numeric values, then retained announcement bindings.** The [revised candidate](8.4-numeric-values.md) first unifies existing effect queries, condition operands and characteristic counts without changing their evaluation points. A subsequent slice supplies named retained choices to that same evaluator and materializes concrete costs/counts/divisions before their existing planners. Resolution-time queries remain distinct from fixed choices; no named card or general script evaluator is needed.
2. **Cost routes first.** Reuse fixed numeric costs and add route composition/selection, avoiding a variable model initially. Define composition for boolean costs such as tap/sacrifice instead of blindly summing or spreading fields.
3. **Stack copying first.** Requires a new stack lifecycle contract and, for permanent spell copies, creation. This has more dependencies than the other slices and should follow their locked announcement model.

The parent order recommends announced variables before cost routes and copying when broadening stack coverage. The owner may instead choose creation or existing-definition validation as the next engine item. Implementation requires an explicitly selected, reviewed contract; these alternatives remain open.

## Stop boundaries

Stop before card-name fields, `eval`/arbitrary expressions, reading X back from current mana, guessed client-only values, bypassed cost planning, copied physical-source movement or a new client component. Any actual project setting belongs in `src/config.ts`; printed values belong in typed definitions. The owner's full debug-snapshot and deferred projection decisions remain in effect.
