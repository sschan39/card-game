# 4.3 — Checkpoint trigger scheduling

Status: implemented two-player APNAP, controller ordering and reconnectable selections. Inspected at `8715503`, 12 October 2026. [Development index](README.md).

## Purpose and structure

Settle state-based actions before pending triggers enter the stack, then gather each controller's required choices.

| Module | Owns |
|---|---|
| `src/engine/game-engine.ts` | Collector/checkpoint loop, room queue and priority gating |
| `src/engine/trigger-scheduler.ts` | `planTriggerScheduling` and `applyTriggerChoice` |
| `src/types/trigger.types.ts` | Queue entries, accumulated selections and resume priority |
| `src/engine/choices.ts` | Feasibility and submitted-answer validation |
| `src/engine/target-groups.ts` / `announced-distributions.ts` | Reused target/division validation |
| `src/types/choice.types.ts` | Typed trigger continuation |

The scheduler groups active-player entries first, then nonactive-player entries. Within a controller's group, multiple entries request an explicit bottom-to-top order. Modes, all target groups and targeted distributions are collected before insertion. An impossible required choice drops an unschedulable trigger without publishing an impossible request. Each scheduling step rereads live state through the checkpoint.

## Flow

```text
Action/resolution gathers triggers → finish atomic work → settle SBAs
 → room trigger queue → APNAP grouping → controller order/modes/targets/divisions
 → insert next object → checkpoint → repeat → restore priority after queue completes
```

Queue and selections are serializable room state. The outstanding choice has one owner/request ID; unrelated actions cannot pass around it. Source information can update as a waiting source departs without retargeting the original identity.

## Extension boundary and remaining work

Use the common choices and target/cost-independent announcement helpers. Multiplayer APNAP needs an explicit ordered player list under 9.2; current active/nonactive grouping is a two-player contract. Do not replace player-selected ordering with discovery order.

## Acceptance evidence

`tests/engine/trigger-scheduling.test.ts` proves APNAP versus discovery order, serialized ordering, modes/all targets, divisions and infeasible targets. `tests/engine/rules-progression.test.ts` proves SBA-before-insertion. The mixed-controller socket scenario in `tests/server/live-routing.test.ts` reconnects through ordering, modes and targets.

## Stop condition

Stop if triggers enter the stack before SBAs settle, a controller's chosen order is silently changed, or missing targets require a second client choice protocol.
