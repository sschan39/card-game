# 8.5 — Catalog and decks

Status: documented backlog; playable content expansion is outside the current engine-first authorization. Baseline: `ad6a96e`, inspected 12 October 2026. Parent: [development index](README.md).

## Purpose and current structure

Provide validated definitions and selectable decks without implying that imported rules text is executable support.

Current modules: `src/library/card_data.json` stores prototype definitions; `src/library/card-parser.ts` parses them; `src/library/card-factory.ts` instantiates them; `src/config.ts` supplies the development deck IDs/setup defaults; `src/engine/room-factory.ts` builds and deals those decks. `CardBlueprint` describes executable effects and abilities, not a complete content-capability manifest. `snapshotSetup` validates setup shape; it does not establish full deck-format legality.

## Proposed boundaries

| Unit | Responsibility | Consumer |
|---|---|---|
| Schema validator | Validate metadata, IDs, effect parameters, ability IDs and references | Catalog loader |
| Capability resolver | Report supported/unsupported required operations and profile rules | Loader, deck validator, developer tools |
| Immutable definition catalog | Resolve validated definitions by ID without mutable fixture state | Instance factory |
| Deck validator | Apply explicit profile rules to submitted definition IDs/counts | Setup/deck selection |
| Deck selection protocol | Persist chosen deck and validation result before setup | Existing room creation/setup |

Definition loading never executes rules text. A capability record must link a mechanic to its handler/schema and acceptance scenarios; a registered string key alone is weak evidence. Unsupported semantics produce an explicit development error/result rather than a silent no-op.

```text
Definition input → schema validation → capability/profile validation
  → immutable catalog → deck validation/selection
  → room-snapshotted setup → ordinary instance creation and gameplay
```

## Extension points

Metadata belongs to definitions; counters/taps/face state belong to instances. Format constraints are profile data, with defaults/settings centralized. Do not alter engine actions for particular catalog IDs. Synthetic definitions in tests can exercise generic mechanics without expanding the playable catalog. Fixtures must clone definitions when mutation is necessary; shared blueprint caches must remain immutable to consumers.

## Slices and acceptance

Design separately: schema/capability validation; immutable catalog interface; deck validation; deck selection; then authorized catalog additions. A card-to-mechanic-to-scenario matrix records declared support and demonstrated coverage separately.

Required evidence: duplicate/unknown IDs fail clearly; invalid effect/ability payloads are rejected; unsupported requirements are disclosed; decks validate under their selected profile; invalid selection cannot partially start setup; both players' accepted deck choices survive reconnect; fixture mutation cannot leak between rooms/tests; definition import counts do not change capability claims. Engine tests and real setup/socket scenarios are both needed.

## Stop conditions

Stop before adding named-card handlers, interpreting rules text through string matching, silent dropping of unknown primitives, or changing engine behavior to accommodate malformed content. Correct the schema/operation contract or seek content-scope approval first.
