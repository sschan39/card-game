# 1.5 — Priority and consecutive passes

Status: Implemented reset and coordinator ownership.

Inspected source baseline: `ad6a96e`, 12 October 2026. [Development index](README.md). Source inspection documents current structure; test paths below identify verification responsibilities, not a new passing run.

## Purpose

Prevent old pass history from resolving the stack or advancing a phase after an intervening action.

## Current structure

- `src/engine/state-machine.ts` — priority/pass planning.
- `src/engine/game-engine.ts` — passPriority, givePriorityTo and stack/checkpoint coordination.
- `src/engine/player-commands.ts` — ordinary pass and debug resolution descriptors.
- `src/types/game.room.types.ts` — priorityPlayerId and lastPassedPlayerId.

Consecutive passes are room state. Successful intervening actions/transitions reset the pass record. Two valid consecutive passes resolve one stack object or progress one authoritative phase step through the coordinator. Debug direct resolution has an explicit mode.

## Flow

```text
Priority holder passes → next player; intervening action → reset; consecutive passes → resolve/progress → checkpoint → priority
```

## Extension boundary

New special actions and decision completions must specify pass-reset and priority consequences in their shared flow. Do not store independent pass booleans on sockets.

## Remaining work and modification notes

Preserve ordinary response windows and debug separation as land/loyalty/shortcut actions are added.

## Acceptance evidence

- tests/engine/rules-progression.test.ts covers pass/action/pass returning priority correctly.
- tests/engine/player-commands.test.ts and tests/server/live-routing.test.ts verify boundary and live routing.

## Stop condition

Stop if a shortcut must consume an opponent's pass, if socket-local state determines priority, or if a resolution bypasses pending rules work.
