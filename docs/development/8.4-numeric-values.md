# 8.4 slices — Shared numeric values and announcement lifetime

Status: Slice A approved, implemented and verified on 12 October 2026; Slice B remains a candidate for its own review checkpoint. Implementation follows the design committed at `ce10198`. Parent: [stack breadth](8.4-stack-breadth.md). Historical source map: [announcement integration review](8.4-announcement-integration-review.md). Execution record: [Slice A plan](8.4-numeric-values-plan.md).

This replaces the earlier X-specific candidate. The owner's direction is one reusable value system across conditions, costs, effects and characteristics. The spelling `X` does not select an evaluator or decide when a value becomes fixed. The work is split into two reviewable engine slices, executed one at a time.

## Need and inspected pre-implementation structure

An announced number and a current characteristic are both usable in arithmetic, but have different lifetimes. If a player announces X=3, later source changes must not change that choice. If an effect reads source power during resolution, earlier effects in the same resolution can change the result. A static power-setting effect can read a creature count on every characteristic evaluation; a resolved stat modifier currently freezes its count when created.

| Current owner | Existing numeric behavior | Gap addressed here |
|---|---|---|
| `effect-resolver.ts`, `buildDynamicParams` | Top-level `DYNAMIC:` source/target power and toughness, plus triggered event paths; evaluated before each resolving instruction | No shared expression or stored binding; query dispatch lives in the resolver |
| `rule-conditions.ts` | Literal values and own-field `{ path }` lookup; comparison and `all`/`any`/`not`; context includes source, controller, event and history | Arithmetic cannot be reused in conditions; nonnumeric comparisons must remain supported |
| `characteristic-layers.ts`, `numberValue` | Count an `EffectScope`, multiply and add using the intermediate layer board | Own count/arithmetic implementation; must not recursively invoke the characteristic facade |
| `continuous-effects.ts`, `normalizeContinuousEntry` | Another count/arithmetic implementation; freezes resolved stat values at creation | Shared calculation needed without changing its retention rule or battlefield default |
| Mana, target and distribution planners | Concrete numbers with their own validation and gameplay rules | Authored expressions must become concrete before these planners run |

This table describes the pre-Slice A source review. Current shared APIs and fresh verification are below. There is still no numeric announcement choice or retained stack binding record in production.

## Approaches

1. **One numeric evaluator with consumer-owned contexts and timing — recommended.** Reuse constants, stored bindings, queries and arithmetic everywhere. Each consumer supplies its view of the world and checks its numeric domain.
2. **Separate mana, power and condition variable systems.** Small changes locally, but repeated syntax, arithmetic and lifetime handling would make later extensions diverge.
3. **A general scripting or reactive-variable framework.** More expressive, but introduces execution, dependency and scheduling machinery beyond this need. Existing layer ordering and instruction sequencing already own those concerns.

## Shared definition contract

These types are now exported from `src/types/numeric-value.types.ts` (the failure branch is also named `NumericFailure`):

```typescript
type NumericExpression =
  | { kind: 'binding'; name: string }
  | { kind: 'query'; id: string; args: Record<string, unknown> }
  | { kind: 'add' | 'multiply'; left: NumericValue; right: NumericValue };
type NumericValue = number | { numeric: NumericExpression };
type NumericBindings = Readonly<Record<string, number>>;
type NumericResult =
  | { ok: true; value: number }
  | { ok: false; reason: 'invalid_expression' | 'missing_binding'
      | 'unsupported_query' | 'missing_context' | 'invalid_number' };
```

The explicit `numeric` wrapper distinguishes an expression from handler-owned parameter objects and existing condition paths. Definitions are serializable data. No functions, executable text, implicit player prompts or mutations occur during evaluation. Bindings are named numbers scoped to the current action/stack/effect context; no global store, automatic inheritance or binding-to-binding dependency graph is introduced.

The evaluator handles only structure, binding lookup, query dispatch, addition and multiplication. Operations run left then right; check finite numeric operands and intermediate results, and reject unsafe integer operands/results rather than accept lost precision. Consumer domains additionally require integer values, bounds or permitted signs where appropriate. Announced inputs must be safe integers; signed effect/stat values are allowed. A missing binding or context is an explicit result, never silently zero. Defaults such as an omitted stat delta being zero belong to the existing consumer adapter, not binding lookup.

Queries are registered engine implementations with argument validation and required context capabilities. Start with two reusable families: `field` reads an own-field numeric path from a supplied rules view using `readRulePath`; `count` applies the existing `EffectScope` matcher to a supplied object/characteristic view. New query families register once and can be used by any consumer that supplies their required context. No handler switches on card names. Unknown queries and malformed arguments reject explicitly.

Transient contexts contain bindings and read capabilities, not persisted callbacks. A normal resolution context can expose exact source information and the first already-revalidated target. A layer context exposes its current intermediate board. Count defaults, controller perspective and available fields are explicitly provided by those adapters. A query reads only that supplied context; it must not reach around it to obtain a different board or source incarnation.

Examples reuse the same stored value without separate mana or power interpreters:

```typescript
const x: NumericValue = { numeric: { kind: 'binding', name: 'X' } };
const xPlusTwo: NumericValue = {
  numeric: { kind: 'add', left: x, right: 2 }
};
const currentPower: NumericValue = {
  numeric: { kind: 'query', id: 'field', args: { path: 'source.power' } }
};
```

| Consumer | Authored value | With stored X=3 | Consumer rule |
|---|---|---|---|
| Generic mana requirement | `xPlusTwo` | 5 | Nonnegative safe integer, then existing payment rules |
| Numeric effect parameter | `x` | 3 | Existing effect's numeric domain |
| Condition `gte` operand | `x`, compared with 3 | True | Existing boolean/comparison structure |
| Static stat delta | `x` | +3 | Signed stat arithmetic, then existing layer ordering |
| Maximum target count | `x` | 3 | Safe integer and feasible min/max group |

This table describes the shared contract. Each integration's availability is tracked below; an expression type alone does not establish all gameplay consumers.

## Evaluation and retention ownership

Expressions do not contain an `evaluateAt` flag. The consuming field's contract selects its evaluation point. To retain a query result, that owner evaluates it at the specified point and stores the resulting number in its existing serialized record. An expression by itself does not create a new retained variable.

| Consumer | Evaluation point | What persists |
|---|---|---|
| Announced binding | Selection before dependent targets/divisions | Chosen number through prompts and then on the committed stack object |
| Variable target cardinalities / announced division total | After bindings, before target/division selection | Concrete schema and allocated amounts for that announcement |
| Mana requirement from bindings | Complete cost calculation before payment | Concrete cost for the transaction; bindings remain recorded on stack |
| Resolution effect parameter query | Immediately before its instruction, using state after earlier instructions | Concrete handler input; not automatically frozen for later instructions |
| Trigger condition / intervening condition | Existing discovery and recheck points | Original event remains a snapshot; live fields are read anew |
| Static continuous numeric expression | Existing layer application/dependency comparison | Expression; recalculate against the intermediate board |
| Resolved continuous stat expression | Existing entry creation/normalization | Concrete numeric stat operation; later board changes do not refresh it |

Event data is retained information even when accessed through a query. Query does not necessarily mean live data. Source information continues through `resolveSourceInformation`: original live incarnation when present, otherwise the retained source information. Target access must use the existing validated exact reference, not rediscover a returned object by UUID alone.

Characteristic adapters use the supplied layer board for both field reads and count matching. They must not call `CardCharacteristicService` from a query while that service is already computing layers. Existing effect dependency ordering remains authoritative; the evaluator does not introduce its own scheduler or cached final-board result.

## Slice A — Implemented shared evaluator and existing consumers

`src/engine/numeric-values.ts` is the common pure evaluator/query-dispatch boundary, with registered `field` and `count` implementations. Typed numeric expressions now work in top-level effect parameters, numeric condition operands and existing continuous stat fields. Existing nonnumeric `RuleValue` literals, paths and `includes` remain under the condition module.

| Implemented unit | Exported boundary / responsibility |
|---|---|
| `numeric-value.types.ts` | `NumericValue`, `NumericExpression`, `NumericBindings`, `NumericResult`, `NumericFailure`, transient `NumericContext`, `NumericQuery` |
| `numeric-values.ts` | `evaluateNumericValue`, `validateNumericValue`, `hasNumericExpression`, `registerNumericQuery`; duplicate query IDs reject |
| `shared/rule-path.ts` | `safeRuleKey`, `validRulePath`, `readRulePath`; old rule-condition import remains re-exported |
| `effect-scopes.ts` | Existing scope matching/defaulting plus `validEffectScope`; `self` matches UUID, zone and revision |
| `numeric-characteristics.ts` | `createBoardNumericContext`, legacy `characteristicNumericValue` translation, `requireCharacteristicNumber`; receives a characteristic reader from its caller |
| `numeric-definitions.ts` | Shared numeric validation for effects, conditions, abilities, blueprints and continuous operations; reserved syntax in unsupported data rejects |
| Existing resolver / conditions / continuous modules | Supply contexts and evaluation points; the proposal planner previews continuous normalization before committing a transaction prefix |

Translate existing `DYNAMIC:` numeric reads and `{ count, multiply, add }` stat definitions through small compatibility adapters into the same evaluator. Do not retain separate arithmetic interpreters. Preserve the existing contexts and sampling points, including resolved-count battlefield defaults versus explicitly scoped static counts. Existing event paths that carry nonnumeric data retain their legacy path behavior; introducing the numeric wrapper makes a numeric requirement explicit rather than reinterpreting every old path as numeric.

New typed numeric failures propagate through a condition tree as unresolved and yield a nonmatch, including under `not`; do not turn a missing numeric operand into a successful negated condition. Existing legacy path/boolean behavior is not silently changed. Resolution preserves the current unresolved-parameter skip metadata. Malformed authored expressions/query arguments fail definition validation; malformed resolved entries fail operation planning before mutation. An unexpected missing capability during characteristic evaluation is a reported engine invariant failure, not a zero stat or partially committed entry.

Only top-level values explicitly wrapped as numeric are evaluated inside effect `params`. Typed mode/choice effect branches are traversed where their owner already selects/executes them. Opaque nested handler data is not recursively interpreted. Unsupported reserved wrappers are rejected by the typed consumer's validation rather than accepted as working expressions.

Bindings are supported by the evaluator with an explicitly supplied record, but this slice creates no player choices or stack binding lifecycle. Existing gameplay consumers reject binding references unless their owner supplies retained bindings. This slice does not claim X casting is implemented.

Acceptance: the same expression yields the same result in effect, condition and stat integrations given equivalent contexts; missing/unknown data, malformed arguments and nonfinite arithmetic produce explicit outcomes; numeric failures under boolean nesting do not become matches. Existing dynamic source/event behavior, sequential state changes, static scope/dependency behavior and frozen resolved counts remain covered. Prove layer queries use the intermediate board and do not recurse into the facade. No new catalog cards or client components.

## Slice B — Announced values using the shared evaluator

After separate Slice B approval, add named numeric declarations to ordinary spell and non-mana activated-ability definitions. Use a list of `{ name, min, max? }` declarations, literal safe-integer bounds satisfying `min <= max` when present, and a `NumericBindings` record. Names must be unique nonempty own-field keys, excluding the prototype-related keys already prohibited by `readRulePath`; invalid/extra names reject. Declarations are independent, selected in authored order; dependent bounds and formula-defined bindings are outside this slice. X is merely one declaration, conventionally with minimum zero. The parser's `{X}` syntax maps to its binding reference; repeated symbols combine with shared arithmetic, e.g. `{2}{X}{X}{R}` is `2*X+2` generic plus one red. Do not infer a declaration from arbitrary rules text.

Two distinct lifecycle moments answer when X is finalized:

```text
Live source/timing and effective definition
  → choose modes
  → choose declared numbers; fix bindings for dependent choices
  → materialize target counts/division totals
  → choose targets and divisions
  → calculate the complete concrete cost
  → plan payment, including existing nested mana activations
  → revalidate source, definition, bindings and completed selections
  → atomically commit payment and stack insertion with retained bindings
  → resolution evaluates its parameters using retained bindings/current queries
```

The selected number is fixed before dependent choices, while the action becomes committed only after successful payment. Cancellation discards the unfinished announcement. Changing a binding before payment starts a fresh dependent selection sequence; it must not reuse prior targets, divisions or payment selections. A player cannot edit the committed record. Failed payment leaves resources unchanged and permits cancellation or a new announcement.

Preparation and final execution reread effective definitions and validate the same supplied bindings. They cannot select a different value, refresh an exact source reference or silently change a previously accepted target schema. Pure recomputation of binding-only expressions gives the same result; changed effective definitions invalidate incompatible selections before payment. Live query-based costs/cardinalities require a separately reviewed freeze/invalidation contract and are not advertised in this slice. Resolution parameters and conditions may combine stored bindings with queries at their already-defined evaluation points.

Keep concrete `ActionCost`, `ManaCost`, target groups and distribution planner inputs numeric. Authored types permit `NumericValue` in the generic mana requirement, target min/max and distribution total. Other cost fields remain fixed for this slice. An action materialization service uses the common evaluator; it is an adapter for these consumers, not another expression interpreter. Resolution materializes top-level numeric parameters just before dispatch, and passes concrete values to existing handlers. A fixed per-target announced division remains fixed and is not redistributed if targets later become illegal.

Stack objects gain an optional retained binding record. Reconnect and JSON recovery carry it through existing room transport. Declaration data follows effective card/ability definitions: layer-1 copies replace or clear it with the copied cost/effects; ability grants carry their own declarations. Static effects do not automatically inherit the X of a spell that created a permanent; entry-value transfer remains a separate creation/lifetime consumer.

Add a discriminated scalar `PendingChoice` branch with range and numeric answer; it has no option-count bounds or fixed allocation total. Preserve existing listed/allocation answers. The action packet supplies a bindings record; omitted declarations prompt in order, malformed supplied numbers reject. Extend the action continuation with binding identity and exact source UUID/zone/revision/ability ID, preserved through all subsequent prompts. A stale source or malformed answer keeps the pending request cancellable and resources intact. Use existing `ChoicePanel` for one integer input, distinguish zero from blank, and preserve existing transport/ownership checks.

Declared-variable actions submit to server choices before local targeting; fixed simple actions retain their current client path. Options describe pending announcement without a false unresolved-cost affordability result. No artificial global cap or new setting is needed; authored bounds and numeric validation apply. Any actual future setting belongs in `src/config.ts`.

For X=0, a zero-target definition and zero division must complete without an impossible allocation prompt. A definition demanding a positive allocation cannot complete at zero; reject before payment rather than clamp. Range checks, concrete costs and target-only legality remain with their existing consumers.

Acceptance: generic spell/non-mana activation fixtures using the same bindings for costs, conditions, effect amounts, target counts and divisions; multiple independent names without separate evaluators; scalar/direct choices, zero and malformed values; exact source departure/return; cancellation and dependent-choice restart; mode/variable/target/division/payment ordering; no partial costs; bindings unchanged after payment/countering/source departure; sequential live queries can change while bindings do not; JSON/reconnect and later selected effect branches retain bindings; effective copies/grants preserve declaration ownership. Add no named card.

## Extension ownership and verification

The shared evaluator owns value syntax/arithmetic/query registration. Conditions own boolean meaning; characteristic layers own their board and ordering; announcement owns selections and commitment; cost/target/distribution planners own concrete gameplay validation. New consumers specify their evaluation point and retained record, then call this evaluator. This allows new mana or power consumers without creating a new variable language.

Slice A integration owners: `rule.types.ts`, `continuous-effect.types.ts`, `card-parser.ts`, numeric definition/entry validation, `rule-conditions.ts`, `effect-resolver.ts`, `continuous-effects.ts`, `characteristic-layers.ts` and `proposed-events.ts`. Slice B will add declaration/stack/choice types, parsing, effective-definition propagation, action choices/options/handlers and existing client targeting/ChoicePanel.

## Stop boundaries

Stop before named-card logic, separate evaluators inside mana/power/effect handlers, arbitrary scripts, automatic scheduling, implicit live-query freezing, hidden client-only state, definition mutation, guessed binding inheritance, invented physical source cards, payment/targeting bypasses or a new client component. Unsupported consumers must be scoped explicitly; Slice B begins only after its owner review checkpoint.
