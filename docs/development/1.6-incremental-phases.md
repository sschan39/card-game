# 1.6 — Incremental phase progression

Status: Implemented one-step live planning.

Inspected source baseline: `ad6a96e`, 12 October 2026. [Development index](README.md). Source inspection documents current structure; test paths below identify verification responsibilities, not a new passing run.

## Purpose

Recompute turn progression after each committed step instead of applying a stale precomputed turn chain.

## Current structure

- `src/engine/state-machine.ts` — planNextStep and phase transition mutations.
- `src/engine/game-engine.ts` — advancePhase and phaseMutations.
- `src/types/game.state.types.ts` — ordinary phase sequence.
- `src/shared/turn-utils.ts` — declaration ownership separate from priority.

The director asks for one step against the current room, commits its effects, settles rules work and then decides whether another automatic step is appropriate. Choices and triggers can stop advancement. Combat declarations are turn-based decisions, not spells.

## Flow

```text
Live room → one PhaseStep → commit entry actions → checkpoint/choice → reread room → next step or response
```

## Extension boundary

Extra/skip turn or phase plans must extend this live cursor rather than reintroducing a full speculative chain. 9.1 owns that broader scheduling model.

## Remaining work and modification notes

Preserve step-entry draw attempts and terminal interruption when adding new phase consumers.

## Acceptance evidence

- tests/engine/ordinary-turn.test.ts, tests/engine/state-machine.test.ts and tests/engine/rules-progression.test.ts cover step order/response/declarations.
- Real-server turn scenarios in tests/server/live-routing.test.ts provide protocol evidence.

## Stop condition

Stop if new progression relies on a cloned room representing an entire future turn or ignores choices/terminal changes between steps.
