# 8.4 Slice B — Retained announcement bindings

Status: minimal Slice B approved, implemented and verified on 12 October 2026. The owner requested minimal scope. Original source review baseline: `a9e8a07`; the broader extension design below remains open. Parent: [shared numeric values](8.4-numeric-values.md). Execution record: [minimal implementation plan](8.4-announcement-bindings-plan.md).

## Implemented minimal contract

Ordinary spells and non-mana activated abilities declare independent named safe integers, choose them through existing action choices, materialize generic mana, and retain their own bindings on the stack. Top-level numeric effect parameters combine these bindings with existing resolution queries. Variable target counts, division totals, nested continuous-operation bindings, new conditions and permanent/triggered/static inheritance are not implemented.

| Actual boundary | Responsibility |
|---|---|
| `NumericDeclaration`, `CardBlueprint.numericDeclarations`, `ActivatedAbility.numericDeclarations` | Explicit declaration ownership; literal bounds and safe unique names |
| `AuthoredActionCost` | `NumericValue` only in generic mana; concrete `ActionCost`/`ManaCost` remain payment planner inputs |
| `numeric-definitions.ts`, `assertNumericDeclarations`, `assertAnnouncementCost` | Declaration syntax, binding-only generic costs, declared references and unsupported-location rejection |
| `announcement-values.ts`, `spellAnnouncementDefinition`, `abilityAnnouncementDefinition` | Relevant effective definition projections; ability ID belongs to the activation projection |
| `prepareAnnouncement` | Validate partial bindings and original source/definition; return missing declaration, copied bindings, snapshot and concrete cost, or an explicit failure |
| `materializeAnnouncementCost` | Shared numeric evaluation and nonnegative safe-integer generic requirement; no payment or mutation |
| `NumericChoice` / `ListedChoice` union | Numeric choice has range and action continuation; listed/allocation choices retain their fields |
| `ActionContinuation.field = 'numericBindings'`, `bindingName` | Answer selects the declared name; saved action data carries `numericBindings` and `AnnouncementSnapshot` |
| Spell/activated `numericBindings` | Copied readonly binding record retained through source departure, JSON recovery and resolution branches |
| Existing ChoicePanel, options and targeting | Scalar input distinguishes blank from zero; declared actions ask the server before local target collection |

The actual minimal flow is modes → independent numbers → concrete cost and existing fixed target/division selections → existing nested mana/payment planning → revalidation → atomic costs/stack insertion → ordinary resolution. The number is fixed for the draft before dependent choices; commitment happens only after successful payment. Cancel and restart to change earlier selections; there is no in-place draft editor.

The saved snapshot contains exact source UUID/zone/revision and the relevant effective definition. Resume compares source and definition structurally, treating omitted optional fields consistently after JSON recovery. Existing timing, control, target legality and affordability checks run again. Bindings belong to the action, including declarations unused by the selected mode. COPY replaces or clears spell declarations; granted abilities carry their own declarations. TEXT replacements preserve binding identifiers and declaration names.

Numeric answer packets use `{ choiceId, number }`; supplied action packets use `numericBindings`. Internal `ChoiceAnswer` preserves existing `values`/`allocations` and carries `number` for scalar answers. No options list is fabricated for a numeric choice. No settings or catalog cards were added.

Verification: 970 tests passed in 75 files, including 36 actual-server scenarios, with two workers. Both TypeScript checks and server/client production build passed. The new engine file covers 29 announcement scenarios; client tests prove scalar submission/blank-versus-zero and authored cost display; the real server scenario covers numeric prompt → reconnect → payment → retained stack record → resolution on both clients. Independent review's TEXT identifier defect was reproduced before its fix; final focused review found no remaining important or critical issues. Historical tests rejecting X/generic arithmetic were revised for the newly supported contract while retaining rejection of hybrid/unknown symbols and live-query costs.

## Broader design retained for modification

The remaining sections describe the original broader candidate. Their variable cardinality/division and nested stat-operation proposals are extension points, not implemented interfaces. The approved minimal contract above takes precedence.

## Problem and example

At the review baseline, the engine could evaluate a numeric expression with supplied bindings, but gameplay had no owner that asked for a number and retained it. Definition validation consequently rejected every binding reference. The minimal implementation now closes that lifetime and generic-cost gap; target counts and division totals still require authored concrete numbers.

A generic test spell declares X, costs X+2 generic mana, targets up to X creatures and divides X damage among its chosen targets. With X=3, it needs five generic mana, allows up to three targets and fixes a total of three damage. The minimal implementation now covers the number prompt, generic cost and retained effect amount; this example's variable target/division contracts remain future consumers. Source power changing after payment must not change X; an explicit source-power query still follows its existing resolution timing.

This example is an engine fixture, not a proposed catalog card.

## Recommended scope and alternatives

The original recommendation grouped declaration ownership, scalar choices, concrete announcement materialization and retained stack bindings. The owner approved a minimal implementation of generic mana and top-level effect parameters first. Variable cardinality/division consumers and nested continuous-operation fields remain additional extensions of the same evaluator.

Adding only a stack `X` field would leave declaration validation, prompts and dependent planners disconnected. Adding generic action and instruction conditions at the same time would expand the work into a separate condition lifecycle, including when a paused conditional instruction decides to execute. The recommendation keeps that missing consumer visible below and does not claim it works.

## Definition ownership and authored/concrete types

Add `NumericDeclaration { name: string; min: number; max?: number }` to the numeric type module. Spell declarations belong to `CardBlueprint.numericDeclarations`; an ordinary activated ability owns its own `numericDeclarations`. Bounds are literal safe integers with `min <= max`; names are unique, nonempty safe own-field keys. Independent declarations are selected in authored order. The absence of a maximum does not disable safe-integer validation. No global cap or new configuration setting is needed.

Introduce authored counterparts for costs, requirements, targeting, effects and modes instead of widening the concrete planner types:

| Authored field | Permitted value | Materialized owner |
|---|---|---|
| Generic mana requirement | Number or binding-only shared arithmetic | `ActionCost.mana.generic` number |
| Target `minTargets` / `maxTargets` | Number or binding-only shared arithmetic | `TargetingDefinition` count bounds |
| Distribution `total` | Number or binding-only shared arithmetic | Existing concrete `EffectChoice` distribution |
| Effect top-level numeric parameter | Shared `NumericValue`, including queries | Concrete handler parameter at resolution |
| Resolved `SET_STATS` / `STAT_DELTA` numeric fields | Shared `NumericValue` in the existing typed continuous-operation location | Concrete stat operation at instruction execution |

Authored costs retain fixed colored/colorless mana and other fixed cost fields. Authored targeting retains fixed structural filters and power/toughness filters. Mode counts and selection/search bounds remain fixed. An authored effect may use variable target cardinality in its targeting or selection criteria, and a variable distribution total; typed option/ordering branches recursively use authored effects. Before stack insertion, materialize those cardinalities/totals throughout the typed branches into existing concrete effect definitions. Numeric effect parameters remain expressions for their resolution owner.

The binding-only restriction is validation of the shared expression tree, not a second expression language: literals, declared references, addition and multiplication are allowed; queries reject in cost/cardinality/total fields. Live-query announcement fields need a separate freeze/invalidation design.

Declaration validation passes an explicit owner into numeric definition validation and parser normalization of effects/modes; validating a child with the old empty-owner default before its parent would incorrectly reject a valid declaration. Spell ownership applies to its cast cost, cast effects and spell modes. An activated ability's ownership applies to its own cost/effects/modes. It does not leak into static abilities, triggered abilities, `onEnterEffects`, COPY blueprints or newly granted abilities. COPY blueprints and granted abilities establish their own declaration scopes. Undeclared references reject even in an unselected branch. Mana abilities cannot declare bindings in this slice.

`{X}` in a mana string translates to the shared binding reference and requires an explicit X declaration. Repeated symbols compose through shared arithmetic; `{2}{X}{X}{R}` means generic 2+2*X and one red. Arbitrary names are available in structured definitions, not inferred from rules text. Unrelated parser repairs, including support for a currently ignored structured ability `effect` field, remain outside this slice; declaration validation must operate on the supported normalized ability path rather than pretend that field already works.

## One announcement preparation boundary

Add a pure `announcement-values.ts` adapter. It validates declaration/binding records, checks binding-only fields and materializes authored cost/effect structures through `evaluateNumericValue`. It returns concrete inputs or an explicit error and never prompts, pays, dispatches effects or mutates definitions.

Choice preparation and both action handlers call this adapter. Avoid independent arithmetic or materialization loops in the handlers. Retain the existing mode selection, targeting, announced distribution and combined cost planners as the authorities for their gameplay rules.

```text
Original source incarnation + effective announcement definition + timing
  -> select modes
  -> validate supplied numbers / prompt for missing declarations
  -> fix bindings
  -> materialize typed target counts and distribution totals
  -> select concrete targets and divisions
  -> materialize complete concrete cost
  -> plan existing nested mana activations and payment
  -> recheck source, effective definition and all concrete selections
  -> existing atomic cost/stack transaction, with bindings on stack object
  -> existing target revalidation and sequential effect resolution
```

All declarations belong to the action, including a declaration used only in a mode that was not selected; the engine prompts for every declaration. This avoids implicit mode-dependent declaration discovery.

## Draft retention, continuations and commitment

Each action continuation retains the source UUID, zone and `zoneRevision`, plus ability ID for activation. Capture it before the first prompt and preserve it through mode, scalar, target, division and payment continuations, including a nested mana choice. A returned object with the same UUID and a different revision cannot resume the announcement.

Retain a serialized snapshot of the relevant effective announcement definition: declarations, cost, base effects, modes and mode count. On every resume and before final planning, compare these fields against the current effective definition. Any change invalidates the draft and requires cancellation/restart; do not silently rematerialize a different cost or target schema. Recheck timing, control, current target legality and affordability independently even when the definition matches. This comparison is scoped to announcement data, not arbitrary card state or the full room snapshot.

Validate a supplied partial binding record before using it: safe own keys, declared names only, numeric safe-integer values in range. Prompt for missing names, distinguishing an absent property from zero. A resumed scalar answer fills only the named declaration from the saved continuation. Players change earlier bindings by cancelling and starting another announcement; no new in-place editing protocol is needed. That restart discards dependent targets, divisions and payment choices.

The original source reference protects only the unfinished announcement. Successful casting performs the existing real hand-to-stack zone transition and captures the resulting stack source normally. Do not force the hand revision onto the stack card. Successful ability activation retains its existing source-information snapshot, including when paying a sacrifice cost.

Spell and activated stack objects gain optional readonly `numericBindings`. Copy the validated record at commitment so later command-data changes cannot alter it. Triggered objects gain no implicit record. Resolution continuations and replacement `afterResolution` continuations already carry the stack object; preserve its bindings through effect replacement and JSON recovery. Cancellation or failed validation spends no resources. Countering never reevaluates the chosen number.

## Scalar choice and client contract

Make `PendingChoice` a union of the existing listed/allocation shape and a scalar numeric shape. The numeric branch has `kind: 'number'`, `range: { min, max? }`, ordinary ID/player/prompt fields and an action continuation identifying the declaration. It has no options, option-count bounds or allocation total. Numeric answers use `{ choiceId, number }`; internal answers distinguish numeric from listed/allocation results.

Extend the existing `ChoicePanel` with a scalar input. Keep its blank value as text until validation so blank does not become zero. The server applies the same safe-integer/range checks. Invalid answers leave the current request cancellable. Narrow every choice consumer by kind; do not create fake options merely to satisfy the old shape.

For actions owning declarations, client targeting returns to the existing command submission path; the server asks for modes/numbers before targets. Existing fixed actions keep their current local targeting behavior. Options describe the required announcement and check access/timing; they do not label an unresolved authored cost affordable or unaffordable. Once materialized, existing payment planners decide affordability.

X=0 must support zero-target, zero-total definitions without an impossible distribution request. A positive minimum or allocation incompatible with zero rejects before payment. Never clamp a chosen value or redistribute an announced allocation when a target becomes illegal.

## Resolution and power consumers

Supply the stack binding record to `buildDynamicParams`' existing numeric context. Each instruction may combine those fixed values with queries evaluated against state after previous instructions. Source/target identity and last-known information rules remain the existing owners.

Top-level power/toughness parameters already feed concrete stat handlers. For `CREATE_CONTINUOUS_EFFECT`, materialize binding-bearing expressions only in the existing typed `SET_STATS` and `STAT_DELTA` power/toughness fields using the same instruction numeric context before dispatch. A binding-bearing expression may also contain queries; that entire expression is sampled at this instruction. Store concrete stat values in the resolved continuous entry. Do not recursively interpret opaque handler data, and do not attach the announcement binding record to static definitions or newly created permanents. Query-only and legacy count stat definitions continue through existing normalization with their established sampling/default-zone behavior.

## Missing condition consumer — explicit follow-up

At this baseline, `RuleCondition` is used in trigger discovery and intervening-if rechecks. `ActionRequirements.condition` is a different `ActionCondition` with zone checks and global flags. Ordinary activated abilities have no condition field, and resolving effects have no predicate field. Therefore no existing ordinary action condition can read an announced binding simply by adding it to a numeric context.

A future generic conditional-instruction consumer should use `RuleCondition` and the same numeric context, not checks such as `if (X > 0)` in a handler. It needs to specify whether a condition is decided before a resolution choice, whether that decision persists across the pause, how selected branches inherit it, and how false versus unresolved conditions appear in completion events. Announcement eligibility conditions are a different evaluation point and need their own explicit contract. Slice B does not implement either consumer or claim binding-based conditions are playable.

This is a scope decision for review, not an implementation shortcut. If conditional instructions are required in the same approved item, expand the design at this boundary before implementation.

## Acceptance and stop boundaries

Cover spells and non-mana abilities with multiple independent names; shared cost/effect/stat/cardinality/division expressions; both scalar and supplied records; zero, missing, extra and invalid numbers; exact source departure/return; effective definition changes; cancellation/restart; nested mana choices; failed payment atomicity; fixed bindings with changing live queries; delayed option/ordering branches; COPY/grant ownership; serialized prompt and stack recovery. Include an actual-server scenario and existing client component tests.

After implementation, run the full suite with two workers, both TypeScript checks, production build and focused code review. Documentation changes alone need links and diff checks, not another full engine test run.

Stop before named-card behavior, a new evaluator, guessed binding inheritance, a new client component, live-query cost freezing or bypassing the existing cost/target/transaction planners. General targeting review, cost routes, stack copies, mana-ability/trigger selection and permanent entry bindings remain separately scoped. Further extension starts only after its owner scope review; the approved minimal contract above is implemented.
