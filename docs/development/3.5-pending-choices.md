# 3.5 — Serializable pending choices

Status: implemented generic choice transport and current action/resolution/trigger/combat/replacement/SBA continuations. Inspected at `c651cda`, 12 October 2026. [Development index](README.md).

## Purpose and current contracts

A decision survives serialization/reconnect and pauses only its owning engine workflow. The room stores data, never a callback or suspended JavaScript closure.

| Module | Responsibility |
|---|---|
| `src/types/choice.types.ts` | `PendingChoice`, option values, answer and discriminated continuations |
| `src/engine/choices.ts` | Feasibility and answer validation |
| `src/engine/action-choices.ts` | Missing announcement fields and completed action-data assembly |
| `src/engine/resolution-choices.ts` | Instruction cursor, prior reports and selected branch replacement |
| `src/engine/game-engine.ts` | Request identity/owner checks and dispatch to continuation owner |
| `src/client/components/ChoicePanel.tsx` | Existing selections, ordering, allocations, cancellation and opponent wait |
| `src/server/sync-service.ts` | Pending request in ordinary deltas/snapshots |

Kinds include modes, targets, selection/options, discard, payment, optional, search, distribution and ordering. Option IDs must be unique/nonempty. Selection answers use known IDs without duplicates and within bounds; allocations use known options, exact totals and limits. Invalid or stale answers retain the outstanding request. Only unpaid action continuations can cancel.

## Flow

```text
Planner requests feasible choice → engine assigns request ID → room/delta/snapshot
 → owner sends choose with request ID → validate answer
 → owning continuation revalidates/resumes → next request or commit/checkpoint
```

Unrelated commands are blocked while a choice exists. Announcement choices pay nothing until full validation. Resolution choices can follow committed earlier instructions while preserving pending trigger proposals; the engine defers the finishing checkpoint. Search values lock zone/revision; ordering currently orders authored branches rather than library card arrays.

## Extension boundary and remaining work

New workflows add a typed continuation and a resume branch, reusing the existing transport/panel. Setup/mulligan and repeated cleanup do not yet have continuations. Library ordering needs the 8.1 contract; it is not supplied by the current branch-ordering kind alone. Full state/options remain available for debugging: private projection is deferred 0.3, so this is not a hidden-information security claim. Durable restart recovery is 9.3.

## Acceptance evidence

`tests/engine/pending-choices.test.ts` covers modes, unpaid costs, search, ordering, allocation, impossible choices, request identity, serialized pauses and pending triggers. `tests/client/pending-choices.test.ts` covers owner/wait rendering and answer callbacks. `tests/server/live-routing.test.ts` resumes resolution and other current continuations after reconnect.

## Stop condition

Stop if a workflow needs a callback in room state, clears a bad request, grants unrelated priority or adds a parallel client choice protocol.
