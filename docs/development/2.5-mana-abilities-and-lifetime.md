# 2.5 — Mana abilities, payment windows and lifetime

Status: selected activated mana abilities and nested payment activations implemented; general timing windows, triggered mana abilities and both-player boundary draining remain open. Inspected at `c651cda`, 12 October 2026. [Development index](README.md).

## Current structure

| Module | Contract |
|---|---|
| `src/engine/mana-abilities.ts` | `isManaAbility`, `manaAbilities`, `manaOutput` |
| `src/engine/printed-abilities.ts` | Prototype plain-land fallback exposed as an effective removable ability |
| `src/engine/action-costs.ts` | `planManaActivation` pays shared costs and produces selected output atomically |
| `src/engine/handlers/tap-for-mana-handler.ts` | Validate/propose use that same planner |
| `src/engine/option-service.ts` | One advertised option per eligible ability/output color |
| `src/engine/state-machine.ts` | Current drain: zero each color of the active player's pool on entering untap |

Current eligibility requires an activated single `ADD_MANA` effect with self/nonrequired targeting, no all-selection and no loyalty cost. Effective abilities supply stable IDs; index selection remains supported. Output is a positive safe-integer amount and a valid color/list. Defined abilities replace the plain-land fallback. The fallback is existing prototype behavior, not a general derivation of basic-land mana abilities.

## Flow

```text
Select eligible effective ability and output color
 → validate timing/permission/use limit → preview shared costs
 → costs + ADD_MANA + ability-use record → checkpoint (no stack insertion)
```

Nested `manaActivations` preview against earlier activations and reserve the casting card. Missing discard selections can pause an unpaid announcement through the existing ChoicePanel. `ActionValidator` still requires ordinary priority; this is not a complete independent mana-payment window model.

## Demonstrated gaps and proposed boundaries

Pool lifetime currently spans ordinary step boundaries and clears only one player at the next untap. Add both-player drain instructions at the actual boundary, in the same authoritative progression batch, with explicit profile/effect exceptions. Do not make the client drain pools. A future payment-window context should authorize eligible mana actions during a payable choice without granting ordinary priority. Triggered mana classification/processing needs its own eligibility contract; it must not treat every mana-producing trigger as immediate.

New rules-profile defaults belong in `src/config.ts`, with per-room snapshots when necessary. Existing `ManaPool.drain` mutates its argument and is not the authoritative phase-transition path; use reducer instructions rather than calling it on room state.

## Acceptance evidence and remaining scenarios

Current support: `tests/engine/setup-mana.test.ts`, `tests/engine/action-costs.test.ts`, `tests/client/mana-options.test.ts` and selected-mana socket scenarios in `tests/server/live-routing.test.ts`. New gates must cover both players at every boundary, mana retention exceptions, paused/reconstructed payment, invalid nested choices, eligible triggered mana behavior and no early checkpoint during payment.

## Stop condition

Stop if mana production bypasses shared costs, a payment window is simulated by granting unrelated priority, or boundary draining requires direct mutation outside reduction.
