# 5.7 — Planeswalker/battle attack destinations

Status: open. Damage recipients and some family settlement exist, but declarations still attack the opposing player. Inspected at `60e9349`, 12 October 2026. [Development index](README.md).

## Current gap

`src/engine/handlers/declare-attackers-handler.ts` accepts attacker UUIDs without destination selection. `CombatDeclaration` in `src/types/effect.types.ts` has no attack destination. `src/engine/combat-service.ts` derives the two-player opponent for unblocked damage; the Trample adapter in `src/engine/combat-rules.ts` does the same. Permanent damage recipients in `src/types/damage.types.ts` therefore do not establish attack-destination support.

## Proposed boundaries

| Unit | Responsibility |
|---|---|
| Declaration contract | Exact player/permanent destination selected per attacker |
| Destination query | Live type/controller/protector eligibility under the chosen profile |
| Combat reconciliation | Handle destination departure/control changes without rebinding a revision |
| Damage recipient planning | Use declared destination for unblocked/spillover assignments |
| Existing declaration UI/protocol | Present and persist supported destination choice |
| Family entry/settlement | Initial loyalty/defense, protector and defeat lifecycle from 8.3 |

## Proposed flow

```text
Choose attacker + eligible destination → validate full declaration
 → lock destination reference → responses/live reconciliation
 → manual allocations to declared destination → shared damage → family SBA/trigger lifecycle
```

## Extension boundary and remaining work

Define rules for a destination leaving before damage, defender ownership and battle protector routing before implementation. Update Trample together with ordinary recipient planning; adding a menu alone is insufficient. Multiplayer combat remains 9.2 and cannot use a single derived opponent. Existing ChoicePanel/protocol should be reused where possible; no named-card destination handler.

## Acceptance evidence required

Player/planeswalker/battle declarations, mixed destinations, invalid ownership/protector, destination departure/reentry, current-controller changes, spillover, damage to loyalty/defense, defeat triggers, stale requests and reconnect all need engine plus actual-server scenarios. Existing `tests/engine/combat-choices.test.ts` provides manual allocation foundations; it does not prove this missing declaration contract.

## Stop condition

Stop if destination support is a damage-only override, a permanent is located by UUID without revision, or the opponent formula is duplicated for each new family.
