# 9.3 — Deterministic replay and durable room recovery

Status: partial serialization/delta timeline foundations; durable commands/snapshots/restart recovery remain open. Inspected at `60e9349`, 12 October 2026. [Development index](README.md).

## Current structure and limits

| Module | Current contract |
|---|---|
| `src/server/state-store.ts` | Synchronous `StateStore` with map-backed `InMemoryStore` |
| `src/server.ts` | Runtime engine/identity/timer maps; recover existing stored room in the same process |
| `src/server/sync-service.ts` | Per-instance sequence map, explicit deltas and JSONL append/read |
| `src/client/store/gameStore.ts` | Apply delta changes and display sequence in recent log; no sequence-gap rejection/recovery |
| `src/engine/effect-context.ts` | In-game shuffle RNG injection, recorded prepared permutation |
| `src/engine/game-engine.ts` / `room-factory.ts` | UUID generation and setup RNG still have runtime defaults |

Room choices/queues/transactions can round-trip as JSON. JSONL records actual batches/deltas from a known baseline; it is not a versioned initial snapshot plus deterministic command journal. Sequence values reset with a new SyncService. Current reconnect finds a live in-memory room; Mongoose being installed does not establish persistence.

## Proposed boundaries and flow

Use a versioned envelope for room/profile/schema version and committed sequence. Separate deterministic command inputs/outcomes from diagnostic timestamps. Persist snapshot/journal and sequence atomically with an explicit failure policy; serialize concurrent commands per room. Select storage and recovery ownership after this contract is designed.

```text
Validated command + expected sequence → serialized room operation
 → prepared deterministic outcomes → commit/journal/snapshot policy
 → publish delta → client sequence validation or gap request
 → restart loader/migration → restore room → register runtime handlers/dependencies → resume choice
```

## Extension boundary and remaining work

Inject/record replay-relevant IDs, setup randomness and clock inputs consistently; functions stay outside snapshots. Load operation handlers before resuming replacement data. Define snapshot/journal consistency, truncation/error handling, migrations and stale/duplicate command policy. Centralize new settings. Private projections remain 0.3; durable storage is not permission to ship hidden data to clients.

## Acceptance required

Replay an entire match identically including IDs/choices, restart during every continuation family, recover after append/commit failures, migrate old snapshots, reject/recover duplicate/out-of-order/missing deltas, isolate simultaneous room commands and preserve terminal state. Existing JSONL/delta tests (`tests/server/sync-service.test.ts`, `tests/engine/operation-outcomes.test.ts`) are foundations, not restart evidence.

## Stop condition

Stop if replay rerolls prepared randomness, storage and published sequence can silently disagree, old state is loaded without schema checks, or restart recovery depends on closures from the prior process.
