# 9.6 — Deployment and operational lifecycle

Status: local Node/Socket.IO production build path exists; hosting choice, durable operation and load/recovery gates remain open. Inspected at `60e9349`, 12 October 2026. [Development index](README.md).

## Current structure

| Module | Contract |
|---|---|
| `package.json` / `tsconfig.json` | Compile server to `dist`, start `dist/server.js` |
| `vite.config.mts` | Bundle current client to `dist/client` |
| `src/server.ts` | Express serves built client, Socket.IO, environment port/default, disconnect grace and final cleanup |
| `src/shared/game-logger.ts` | Structured contextual logs and injectable sinks |
| `src/server/sync-service.ts` | Synchronous local JSONL diagnostic append |
| `legacy/wrangler.jsonc` | Legacy assets path `public`; does not declare deployment of current Node/Socket.IO server |

The built server/client can run locally. Current room state is in memory, so process restart loses rooms. CI build success is not evidence of an active hosted release. Legacy Wrangler assets do not match the current `dist/client` output/server architecture.

## Proposed boundaries and flow

Select the hosting/runtime path explicitly, then define build artifacts, runtime configuration, socket/proxy behavior, startup/shutdown, health/readiness and log/storage ownership. Integrate 9.3's recovery before claiming durable production readiness. Any new project defaults belong centrally; environment input remains a deployment boundary rather than scattered handler settings.

```text
Verified build artifacts → chosen runtime/configuration → start and restore rooms
 → serve static client + sockets → structured operational observations
 → graceful shutdown/persist/dispose → recovery/load verification
```

## Extension boundary and remaining work

Update or retire Wrangler after hosting is chosen; do not deploy a second stale frontend as if it were the application. Measure synchronous log impact and room/socket/timer lifecycle under load before changing sink/storage architecture. Multi-process hosting requires explicit room ownership/serialization and sequence delivery, not merely additional replicas. Do not provision/publish a hosting service from this documentation task.

## Acceptance required

A selected deployment command serves the same verified client/server, reconnect works through the actual proxy, startup restores durable rooms, shutdown releases listeners/timers, load tests keep rooms independent, failed storage/log writes follow the chosen policy, and operational logs identify room/command/batch without a card-specific logger. Hosting/recovery evidence remains missing today.

## Stop condition

Stop if deployment bypasses the authoritative server, assets come from an obsolete build path, or an operational failure is hidden by swallowing persistence/log errors.
