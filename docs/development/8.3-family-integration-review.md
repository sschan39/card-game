# 8.3 review — Card-family integration gaps

Status: source review complete; next implementation slice not selected or approved. Inspected baseline `f54f219`, 12 October 2026. Parent: [additional card families](8.3-card-families.md).

## Present consumers

The nine checked-in definitions in `src/library/card_data.json` use Creature, Land and Spell types. Their declared effects/abilities cover discard, mana, stat changes, life changes and countering. None declares token creation, permanent/stack copying, loyalty costs, a Battle or a second face/part. Existing family tests seed the relevant state directly.

This establishes an engine coverage gap rather than a failure of a currently authored family action. The owner's reveal and Equipment deferrals remain specific decisions; this review does not silently defer all of 8.3 or authorize new catalog content.

## Source boundaries and missing paths

| Concern | Authoritative current behavior | Missing integration |
|---|---|---|
| New physical instance | `src/library/card-factory.ts` allocates a UUID for a catalog ID and initializes it in library state through `createCardState` | A normal resolving effect cannot create a token from a generic definition and commit its entry |
| Initial state | `src/engine/zone-transitions.ts` constructs empty counters and untapped state; true movement resets active state while preserving UUID | Entry counters/orientation and other authored entry state must exist at the first observable entry, with appropriate replacement handling |
| Mutation boundary | `src/types/game-mutation.types.ts` has ordinary movement, setup-zone replacement and token cessation; `game-reducer.ts` applies them | There is no creation mutation; `SET_PLAYER_ZONES` is explicitly setup-only and `MOVE_CARD` requires a real source occupant |
| Replacement boundary | `src/types/proposed-event.types.ts` / `src/engine/proposed-events.ts` represent zone transfers, draws, damage and resource/counter changes | Creation/entry needs an explicit proposed-event contract before replacement choices can suspend and resume it |
| Token departure | `state-based-planner.ts` schedules cessation outside the battlefield; `zone-transitions.ts` rejects further movement of a departed token | These consume an existing token; they do not create one |
| Copiable values | `card-characteristic-service.ts` already exposes `resolveCopiableBlueprint`; layer 1 `COPY` changes derived characteristics; source snapshots retain departure information | Creation from the query's result; limits on copied definition fields; entry and lifecycle for the newly created object |
| Stack copies | `src/types/effect.types.ts` has spell/activated/triggered objects carrying physical source cards; `effect-resolver.ts` moves resolving spell sources out of stack | A copy's independent stack identity, locked choices and structural destination without pretending it is a newly cast physical card; owned by [8.4](8.4-stack-breadth.md) |
| Loyalty | Parser preserves `cost.loyalty`; `action-costs.ts` rejects unsupported cost keys; `turn-history.ts` counts uses by UUID/revision/ability ID | Signed payment, loyalty-specific timing and a shared per-incarnation limit across loyalty abilities, plus entry counters |
| Battle combat | `declare-attackers-handler.ts` accepts attacker UUIDs only; `CombatDeclaration` has no destination; `combat-service.ts` derives the opposing player for unblocked damage | Explicit player/permanent attack destination carried through declaration, reconciliation, allocation, options and submission |
| Battle lifecycle | Damage removes defense; SBAs handle zero defense, protector selection and a waiting Siege trigger | Defense at entry and the complete defeat/face/access flow; a waiting-trigger check alone does not implement defeat |
| Faces/parts | `CardBlueprint` describes one definition; `CardState` has no selected face/part; parser/factory load one blueprint | Physical definition versus active characteristics, announcement part selection, transform state and zone-appropriate access |

Artifacts and enchantments use the existing type/characteristic and permanent-resolution paths. Their type labels do not justify additional action pipelines. Specific authored mechanics still require their own supported operations.

The structural permanent predicate in `src/engine/effect-resolver.ts` currently lists Creature, Artifact, Enchantment and Land. It omits Planeswalker and Battle, so a spell with only either omitted type resolves to graveyard through the current structural path. Entry support for those families must also address classification; adding counters alone is insufficient. This was identified during the subsequent [8.4 review](8.4-announcement-integration-review.md), against baseline `21afb78`.

## Concrete scenarios

**Creation:** a generic effect instructs its controller to create two 1/1 creatures. The factory can make catalog cards during setup, but no registered gameplay operation plans new token identities and commits their entry. Inventing two cards in a hand and moving them would give observers an incorrect zone history and abuse the existing identity/reset contract.

**Loyalty:** a seeded permanent has three loyalty and two abilities costing +1 and -2. Today either cost is rejected as unsupported. Allowing the counter change alone would still leave entry setup and the shared use limit wrong: the existing ability-specific history key does not prevent activating the other loyalty ability in the same turn.

**Battle:** a seeded Battle can lose defense when a damage assignment names it. An ordinary unblocked attack still damages the opposing player because the declaration has no destination. Damage-recipient support does not prove that the Battle can be attacked through normal commands.

## What the tests establish

- `tests/engine/state-based-extended.test.ts` seeds a token, proves its death event then cessation, and seeds zero-loyalty/defense permanents for cleanup. It does not establish token creation or entry counters.
- `tests/engine/m7-boundaries.test.ts` exercises departed-token movement restrictions and cessation on the stack while retained abilities survive.
- `tests/engine/continuous-layers.test.ts` installs a `COPY` layer from a donor blueprint and checks later modifiers, keywords and original-blueprint preservation. This is characteristic copying, not copied-instance or stack creation.
- `tests/engine/source-information.test.ts` covers live/departed source information and persistent identity across return. It is a dependency to reuse, not a creation test.
- `tests/engine/setup-mana.test.ts` explicitly rejects loyalty costs in the mana-activation path. Successful signed loyalty activation remains unproved.

These are source observations; no tests were rerun for this documentation review and no new family-completion claim is made.

## Next-slice choices

1. **Generic token creation, when extending family coverage.** Establish one creation/entry boundary, new identity allocation and actual entry events through the existing replacement/checkpoint/sync flow. Use a synthetic generic effect fixture; no named playable card is required. This is the first dependency in the parent plan and later supports copied permanent creation.
2. **Loyalty actions first.** Has an explicit unsupported cost field, but entry initialization and shared activation-limit scope must be included. Simply allowing the key would produce a partial family implementation.
3. **Leave family implementation open and review stack breadth next.** Appropriate if the owner wants current consumers to determine new mechanics. This keeps family scope visible rather than labeling unused foundations complete.

Before choosing creation, specify whether the first slice covers only plain creature tokens or general authored entry state, how replacement redirection/cancellation affects existence, where stable identities are allocated across paused choices, and what simultaneous entrants observe. Do not call a narrow insertion operation complete token support if those contracts remain unspecified.

Equipment, Aura binding and reveal records are not prerequisites for plain token creation. Copied permanent spells, loyalty entry and Battle/face workflows must receive separate designs before their consumers are added.

## Stop boundaries

Stop before fake source-zone occupants, setup mutations in normal resolution, card-ID entry branches, UUID allocation during repeated reducer preview, or a copied spell moving its original source card. Stop before automatic Battle face/cast behavior or additional combat-keyword consumers. Preserve the existing manual combat allocation and centralized configuration policy.
