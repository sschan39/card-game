# 8.4 — Payment cost routes

Status: payment-only scope implemented and verified. Baseline `2774e9b`, 12 October 2026. Parent: [stack breadth](8.4-stack-breadth.md). Execution: [implementation plan](8.4-cost-routes-plan.md).

## Gap and scope

At the baseline, each action supplied one authored cost. Combined mana/life/discard/orientation/source-sacrifice costs already used one atomic planner. This slice adds an authored alternative, a retained route selection, and composition with a mandatory extra cost. For example, pay three generic mana or two life, and discard one card either way.

Implement this for spells and ordinary activated abilities through the existing announcement and payment pipeline. No optional additional costs, discounts, cost-dependent effects, targeting changes, copied spells, new payment windows or catalog entries. Mana abilities retain their current fixed-cost contract. No new settings or stack fields.

## Contracts and boundaries

Exported `CostRoutes` contains `alternativeCosts?: { id: string; label: string; cost: AuthoredActionCost }[]` and `additionalCost?: AuthoredActionCost`. Spell `castRequirements` and ordinary activated abilities carry these fields. Each alternative replaces the complete base cost; the mandatory additional cost applies to every route. Numeric generic requirements use the owner's existing declarations.

`CostRouteSelection` is `{ kind: 'base' } | { kind: 'alternative'; id: string }`. Existing actions without alternatives need no route selection; an explicit base selection is also accepted because their base route already exists. With alternatives, omitted selection opens a single-choice prompt containing base and alternative routes. Supplied malformed or unknown selections reject. The packet chooses a route, never supplies its costs.

| Module | Responsibility |
|---|---|
| `src/engine/cost-composition.ts` | Validate cost/route structure and combine concrete costs; no room mutation or payment |
| `src/engine/numeric-definitions.ts` / `src/library/card-parser.ts` | Validate authored ownership and normalize route definitions |
| `src/engine/announcement-values.ts` | Validate route selection, retain definition/source continuity, materialize and compose one cost |
| `src/engine/action-choices.ts` | Existing modes/numbers, then route choice, followed by existing targets and payment prompts |
| Existing action handlers / `action-costs.ts` | Reject incomplete selection and plan the one derived cost atomically |
| Existing options, client routing and ChoicePanel | Allow unresolved alternatives/numbers to reach server choices; check known combined costs for affordability; reuse ordinary list rendering |

Mana colors/generic, life and discard add with safe-integer overflow rejection. True orientation/sacrifice requirements may occur once: duplicate tap, untap or source-sacrifice rejects, as does tap plus untap. False/absent requirements add nothing. Do not collapse two tap or sacrifice payments into one. Unsupported costs, including loyalty, retain their existing rejection boundary.

```text
Effective definition + source incarnation
  → modes and declared numbers
  → choose base or alternative route
  → materialize selected cost + mandatory additional cost
  → one concrete combined cost
  → existing targets, nested mana/discard/payment prompts
  → revalidate source, definition and selections
  → existing atomic payment and ordinary action commit
```

The source/definition snapshot includes all cost routes and remains in the unfinished action through JSON recovery and cancellation. Route information serves payment only and adds nothing to resolution. A later cost-dependent effect needs a separately reviewed retained announcement contract.

Actual exported helpers are `actionCostError`, `assertAuthoredCostShape`, `assertCostRoutesShape` and `composeActionCosts` in `cost-composition.ts`, plus owner-aware `assertCostRoutes` in `numeric-definitions.ts`. `action-costs.ts` re-exports `actionCostError` for existing consumers. `prepareAnnouncement` returns `missingCostRoute` until a route is selected and exposes only the combined concrete `cost` after all required selections. `ActionContinuation.field = 'costRoute'` assigns the existing list answer's first value to action data. Choice IDs are `base` and `alternative:<authored-id>`; the values are the typed selection objects, never authored costs.

## Alternatives considered

Separate action IDs would duplicate announcement and payment logic. A general modifier/optional-extra framework would broaden this slice beyond the approved payment need. Extend the existing announcement adapter and reuse the atomic planner.

## Acceptance and stop boundaries

Prove both base and alternative payments, mandatory extras on every route, combined generic/colored costs, existing bindings, cancellation and reconnect, stale source/definition rejection, nested mana source reservation, malformed selections, duplicate resource requirements and overflow. Failure pays nothing; successful payment occurs once. Existing ChoicePanel renders/submits the route as a normal list choice. Ordinary resolution remains unchanged.

Stop before paying during resolution, treating an alternative as a new action, modifying targeting/effect semantics, adding card-name branches, silently discarding unsupported fields or inventing a cost modifier framework.

## Verification evidence

`tests/engine/cost-routes.test.ts` covers 36 scenarios: both routes, mandatory extras, colored/generic composition, parser/declaration ownership, incomplete direct handlers, malformed selections, overflow/duplicate source requirements, affordability, JSON cancellation, exact source/effective-definition continuity, ordinary abilities, nested mana source reservation and failed-payment rollback. Initial feature run had 22 expected failures before implementation. Independent review reproduced two failures where fixed mandatory extras incorrectly deferred affordability; options now derive their known combined cost through the same adapter. Existing client tests render and submit route IDs through the list form. The actual-server scenario selects the alternative, reconnects during mandatory discard, commits payment once and resolves through both clients.

Full suite passed 1008 tests in 76 files, including 37 actual-server scenarios, with two workers. Both TypeScript checks and server/client production build passed. Final independent review found no remaining important or critical issues. All 221 local Markdown links across development documents and the roadmap resolve. No new catalog entries, settings, component, action or stack fields were added.
