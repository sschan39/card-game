# 9.2 — Multiplayer and format profiles

Status: documented future scope; specific formats/rules/UI are not yet authorized or specified. Inspected at `60e9349`, 12 October 2026. [Development index](README.md).

## Current two-player assumptions

| Module | Current assumption |
|---|---|
| `src/types/game.room.types.ts` | `player1Id`/`player2Id`, one active player and priority holder |
| `src/engine/state-machine.ts` | Toggle turn/pass opponent between those two IDs |
| `src/engine/trigger-scheduler.ts` | Active versus nonactive grouping |
| `src/engine/combat-service.ts` | One derived defending opponent |
| `src/server/reconnect.ts` | Room membership recognizes two slots |
| `src/shared/action-permissions.ts` | Self/opponent relationships, no team model |

Some SBA protector code enumerates `room.players`; that does not make priority, elimination, combat or the protocol multiplayer-complete. Setup fields are development defaults, not a format-profile framework.

## Proposed structure and flow

Define a selected format profile before implementation. It must state player order/teams, starting resources, deck legality, command-zone objects, loss/elimination and any special rules. Separate stable participant identities from turn/priority order, and expose relationship queries rather than repeating “other player” formulas.

```text
Selected profile + participants → validate setup/decks
 → room-owned seating/relationships → priority/APNAP/turn/combat queries
 → profile-aware settlement → reconnect/public views
```

## Extension boundary and remaining work

Commander, team and other variants are not interchangeable additions. Choose one bounded profile with authoritative semantics/UI, then audit every two-player consumer. General command-zone support requires room-card lookup, movement, effects, permission and sync together. Keep profile settings centralized and snapshotted; do not spread format-name branches through engine handlers.

## Acceptance required

Three-or-more participant priority cycles, elimination during stack/choices, multi-controller APNAP, attack destinations/defenders, team targeting, reconnect of remaining players, profile-specific deck/setup validation and simultaneous outcomes need end-to-end evidence. Existing two-client tests cannot prove these requirements.

## Stop condition

Stop if a format is implemented by guessing missing rules, reusing one opposing-player field for multiple defenders, or assuming iterating `room.players` completes multiplayer support.
