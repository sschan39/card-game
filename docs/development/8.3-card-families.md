# 8.3 — Additional card families

Status: partial state foundations; creation and family actions remain open. Baseline: `ad6a96e`, inspected 12 October 2026. Parent: [development index](README.md).

## Scope and existing foundations

This roadmap row contains independent subsystems. Each must receive a bounded design and implementation cycle rather than one combined handler. Artifacts/enchantments do not need a parallel engine merely because their card types differ.

| Family | Existing source evidence | Missing generic behavior |
|---|---|---|
| Tokens | `CardInstance.isToken`; cessation and post-departure movement restriction in `state-based-planner.ts` / `zone-transitions.ts` | Creation with controlled identity, ownership, characteristics and entry events |
| Copies | `COPY` in `continuous-effect.types.ts`; layer 1 in `characteristic-layers.ts`; copiable departure information | Permanent/token creation from copiable values; spell/ability copying and copy-specific stack lifecycle |
| Planeswalkers | Loyalty counter damage in `damage-keywords.ts`; zero-loyalty SBA | Entry counters; payable signed loyalty changes; loyalty-specific timing and shared use limit |
| Battles | Defense damage, protector state/choice and Siege waiting-trigger SBA | Entry setup, attack destinations and full defeat/face workflow |
| Multi-part cards | Single `CardBlueprint` on each instance | Face/part selection, characteristics by zone, transforming/split/adventure timing and retained identity |

`ActionCost.loyalty` is declared, but `actionCostError` in `src/engine/action-costs.ts` rejects keys outside mana/life/tap/untap/discard/sacrifice. Its presence currently excludes mana-ability classification; it does not prove loyalty payment works.

## Proposed subsystem structure

### Creation

Creation planning accepts a generic definition or copiable snapshot, owner/controller, quantity and caller-provided identities. It returns replacement-aware creation/entry instructions. The reducer creates instances once; creation is not a `MOVE_CARD` from a fictitious zone. Entry characteristics/counters must exist at the first observable battlefield state before SBAs.

Do not reuse the rule that resets an existing instance on zone movement to manufacture a new physical identity. Existing objects keep their UUID; newly created objects receive new UUIDs.

### Copying

Separate characteristic copying, creating a copied permanent/token, and copying a stack object. They share a copiable-value query, but have different state lifetimes. A stack copy must not masquerade as a physical card occupying a player's hand. Decide the stack representation and structural-resolution destination contract before adding handlers.

### Loyalty actions

Extend shared cost planning to validate a signed loyalty change. Positive, negative and zero changes all identify loyalty activation. A loyalty use limit belongs to the permanent's current incarnation across its loyalty abilities, rather than to one ability ID alone. Use existing history infrastructure with an explicit limit scope, not an extra boolean on each card.

### Battles and attack destinations

Attack declarations need a destination discriminated by player or permanent reference. Combat reconciliation, damage recipients, options and client submission must consume the same representation. Entry defense and protector decisions precede ordinary SBA settlement. Full defeat behavior depends on trigger/face/permission contracts and must not be inferred from merely reaching zero defense.

### Multi-part definitions

Keep physical definition and active face/part state separate. Zone-appropriate characteristics belong in the characteristic facade; casting chooses an eligible part through announcement. Transforming is not automatically a zone move. Adventure-style exile access uses 8.1's generic cast permission rather than a named-card exception.

## Common flow

```text
Definition / copiable values / selected face
  → validate generic family operation
  → plan identity, entry state or shared action costs
  → replacement-aware commit
  → actual entry/counter/stack/face events
  → existing characteristic queries and checkpoint
  → existing delta/reconnect transport
```

## Order and extension points

Design separately: creation → permanent/token copies → loyalty actions → permanent combat destinations/battles → face/part model. Stack copying is shared with 8.4 and has one owner there. Entry initialization is a general structural contract used by token/counter/attachment families; do not repeat entry fixes in each handler. Settings stay centralized; rule parameters and printed values belong to typed definitions.

## Acceptance evidence

Extend `tests/engine/state-based-extended.test.ts`, `tests/engine/zone-transitions.test.ts`, `tests/engine/continuous-layers.test.ts`, `tests/engine/source-information.test.ts`, `tests/engine/action-costs.test.ts`, `tests/engine/activate-ability.test.ts`, combat tests, sync tests and actual-server scenarios.

Creation must conserve existing identities and allocate unique new ones; simultaneous entrants/witnesses see the proper board; replacement choices resume without duplicate creation. Copies use copiable values rather than all temporary modifications. Loyalty rejects unpayable costs without partial payment, supports zero/+ changes and shared use limits, and survives countering after payment. Battles have entry counters before SBAs and exact combat destinations. Face changes update characteristics without accidentally resetting identity; casting a selected part round-trips through choices/payment/reconnect. No family is complete from state-based cleanup fixtures alone.

## Stop conditions

Stop if any family needs fake zone occupants, card-specific entry counters, new objects on ordinary zone moves, hand-only workarounds for copies, one boolean per named ability, or face checks scattered among legality consumers. Resolve the common structural representation first.
