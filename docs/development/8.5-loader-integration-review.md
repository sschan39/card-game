# 8.5 review — Catalog normalization and deck setup

Status: source review and isolated parser probe complete; implementation contract not approved. Inspected baseline `adef9db`, 12 October 2026. Parent: [catalog and decks](8.5-catalog-and-decks.md).

## Current loading flow

```text
Checked-in JSON definition map
  → lazy normalizeCard on getBlueprint(card ID)
  → shared cached blueprint
  → new UUID plus independent active card state
  → configured development deck
  → fresh setup arrays, shuffle and deal
  → setup mutations and ordinary gameplay
```

The catalog contains nine definitions. `src/config.ts` configures a nine-card development deck with three definition IDs, rather than letting each player select a deck. `createRoom` snapshots setup and resolves every configured ID before returning the room. The existing source intentionally separates fresh setup arrays from ordinary gameplay movement.

## Existing checks and their limits

| Path | Current behavior | Missing boundary |
|---|---|---|
| `src/config.ts` | Validates life, hand size, deck shape and setup flags; clones settings | Definition capability, format legality and player deck selection |
| `src/engine/room-factory.ts` | Resolves configured IDs, instantiates cards, shuffles/deals fresh arrays, emits setup zone mutations | Submitted per-player deck validation/selection and selected-deck recovery |
| `src/library/card-factory.ts` | Unknown catalog ID throws; one lazy blueprint cache entry per map key; instances share that blueprint | Enforced immutable definitions; validate map-key/definition-ID consistency and all loaded semantics |
| `normalizeCard` | Requires a truthy ID; rejects missing/duplicate ability IDs; normalizes selected fields | Full ID/type/shape checks; preservation of supported definition fields; explicit handling of unsupported fields |
| `parseManaCost` | Rejects unsupported symbol syntax and parses fixed numeric/color symbols | Numeric overflow/range validation at definition loading; X remains pending [8.4](8.4-announced-x.md) |
| `normalizeActionCost` | Converts booleans, defaults selected numeric fields, copies mana and numeric loyalty | Reject malformed values and unknown cost keys before normalization can erase them |
| `normalizeAbility` | Recognizes static/triggered; other types fall through to activated; reads legacy `effectId`/`params` | Validate discriminant; define support/precedence for structured `effect`; avoid losing authored semantics |
| `normalizeEffect` | Copies an action string, params, tags, targeting and choice without handler/schema validation | Unknown operations and malformed parameters must be disclosed before gameplay |
| `parseAll` | Preserves outer map keys while independently normalizing inner IDs | Reject mismatched keys/IDs and duplicate logical IDs; JSON object keys alone do not establish identity consistency |
| `src/engine/effect-resolver.ts` | Dispatches only when the effect handler exists; missing handlers produce no mutations | Unsupported operation diagnostics; ordinary completion metadata currently does not add an unknown-handler reason |

`CardBlueprint` includes `superTypes` and `attachmentRequirements`, but `normalizeCard` does not emit either field. The static/effective-characteristic and attachment tests can seed those fields directly, which does not prove JSON imports preserve them. Restore supported fields through a shared normalization contract when this slice is approved; deferred attachment gameplay does not authorize implementing equip.

The factory's shared blueprint reference is visible in source: `getBlueprint` returns its cached object and `instantiateCard` stores that object directly. TypeScript `readonly` declarations do not freeze nested runtime values. Fixture code must clone or replace definitions before editing them; current discipline is not an enforced immutable API. The immutable catalog boundary is shared with [9.5 fixture isolation](9.5-quality-gates-and-fixture-isolation.md).

## Verified parser observations

An isolated Node probe loaded the current `src/library/card-parser.ts`, transpiled that source in memory with the installed TypeScript compiler, and executed its exported normalization functions in a separate VM. It used synthetic input only; no production catalog/cache was modified. The command exited 0 with these observations:

| Synthetic input | Actual normalized result |
|---|---|
| Ability `type: 'unrecognized-kind'` | `type: 'activated'` |
| `effectId: 'UNKNOWN_OPERATION'` | Unknown action string preserved |
| Cost `{ unknownResource: 2 }` | Unknown cost field absent |
| Cost `{ tap: 'false' }` | `tap: true` |
| Blueprint `superTypes: ['Legendary']` | Field absent |
| Blueprint `attachmentRequirements` | Field absent |
| Activated ability authored as `effect: { action: 'MODIFY_LIFE', ... }` | Normalized effect action is the empty string |
| Map key `externalKey` containing definition ID `differentId` | Mismatch accepted |

These are reproductions of normalization behavior, not a full-suite result or evidence that the current nine definitions use every problematic shape. Existing abilities in the checked-in catalog use the legacy `effectId` form. No catalog completion claim follows from successful parsing.

## Why a shared loader change matters

A developer adds a generic ability using the engine's structured `ActivatedAbility.effect` shape. The importer keeps its ability ID but replaces its effect with an empty action, and the resolver has no handler for that action. Investigating payment and stack resolution would miss the earlier semantic loss. A clear normalization error or an explicitly supported structured form makes the cause visible where the definition enters the engine.

Similarly, adding an unknown mandatory resource cost currently loses that cost during normalization. Runtime `actionCostError` cannot reject a key that has already disappeared. Definition validation must inspect raw keys/values before coercion and defaults, then produce the normalized executable representation.

These examples justify reviewing the existing loader independently of importing new cards. They do not require a named-card branch, text interpreter, deck UI or full capability manifest in the first slice.

## Responsibility split when implementation resumes

1. **Pure shape validation and normalization:** validate input before defaulting/coercion; preserve known supported fields; define legacy/structured ability precedence; reject contradictory forms and unknown discriminants/costs with a useful definition path.
2. **Executable capability validation:** resolve operations and parameter schemas through an extensible contract after the relevant engine registrations exist. Keep this distinct from parsing to avoid importing an incompletely initialized engine registry into the pure parser. A handler name alone does not prove all mechanic semantics.
3. **Catalog identity and immutability:** validate map-key/ID consistency, then expose definitions through the selected immutable boundary. Tests requiring synthetic edits must get isolated data.
4. **Deck validation and selection:** consume the validated catalog under an explicitly selected format/profile; persist per-player choices before setup. This remains separate from schema checks and content additions.

The narrow first candidate is definition-preserving normalization with explicit malformed/unsupported-shape errors. Capability ownership/registration order and the immutable cache API need their own reviewed interfaces. Do not silently combine this with the pending X slice or add a heavyweight schema framework solely for this review.

## Existing and required acceptance evidence

`tests/engine/activate-ability.test.ts` checks duplicate ability IDs. `tests/engine/setup-mana.test.ts` checks fixed mana symbols and rejects X/hybrid syntax. `tests/engine/pending-choices.test.ts` preserves ability resolution choices, and `tests/engine/trigger-matching.test.ts` checks trigger filters. `tests/engine/room-factory.test.ts` covers configured deck ownership, card multiset, shuffle and dealt hands. None of those checks alone proves complete raw definition validation.

Future acceptance must reproduce the probe cases before fixing their contracts; round-trip known fields/legacy and structured forms; reject unknown operations/parameters at the chosen capability boundary; prove malformed definitions do not become cheaper or different actions; verify cache/fixture changes cannot leak across instances/rooms; and retain configured setup behavior. Full player deck selection additionally needs invalid/valid submitted deck cases and actual-server reconnect coverage. No existing test suite was rerun for this documentation-only audit.

## Stop boundaries

Stop before playable catalog expansion, rules-text matching, card-ID repair logic, silently dropped mandatory mechanics, fixture mutation of cached definitions or invented format limits. A format policy belongs to its profile; actual settings remain centralized. Existing definition validation can be an engine task, while new content, custom cards and deck presentation still require their own scope.
