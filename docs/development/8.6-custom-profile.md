## Evidence and purpose

The historical inventory is in `docs/superpowers/specs/2026-08-30-continuous-effects-and-modifiers-design.md`, sections 12–12.1, and `docs/superpowers/specs/2026-08-30-deferred-work-and-next-phases.md`, section 4. It describes 24 custom cards and Scorch, chain prevention, reveal casting, equipment, discard costs and usage limits. Historical completion labels are not evidence that the current engine implements those cards. The current prototype input is `src/library/card_data.json`.

This item first reconciles authoritative card text/data and the mechanic inventory. Do not manufacture definitions from remembered descriptions. Missing authoritative card data is an explicit blocker for claiming complete content coverage, not a reason to create approximate card rules.

## Proposed profile structure

| Unit | Responsibility |
|---|---|
| Custom profile definition | Declares custom setup, terminology, thresholds and rule deviations independently of the MTG profile. |
| Mechanic definition | Serializable parameters/conditions using generic counters, events, replacement operations and effect primitives. |
| Registered consumer | Focused rule operation only where existing generic primitives cannot express the confirmed semantics. |
| Requirement matrix | Maps each confirmed card requirement to profile, mechanic definition, generic engine dependency and executable scenario. |

Custom thresholds such as an “ability total” need a defined characteristic/query and authoritative source semantics. Do not infer them from the number of engine ability entries. Chain prevention must define what counts as a chain, who chooses and its lifetime before reusing finite shields.

```text
Confirmed source text → reconciled requirements → explicit custom profile
  → generic dependency check → mechanic definitions/registered operations
  → synthetic engine scenarios → separately authorized content definitions
```

## Reuse and extension boundaries

- Reveal casting needs consumer-specific visibility and casting-access contracts through 8.1's shared flow. The [reveal proposal](8.1-reveal-lifecycle.md) is deferred until a concrete consumer establishes whether an immediate event or persistent information is needed; a record/lifetime model is not a universal prerequisite. Custom content is not currently approved to resume that scope.
- Equipment consumes 8.2's eventual shared attachment/activation flow. [New attachment and equip operations](8.2-attachments.md) are deferred until a concrete consumer needs them; historical custom requirements do not override that decision.
- Discard costs consume `planActionCosts`; turn limits consume event-derived history with the proper scope.
- Counter-based custom behavior consumes generic counter events and characteristic queries. It must not silently become an unconditional MTG SBA rule.
- Prevention consumes the serializable replacement registry/continuations in Milestone 7, after its custom semantics are confirmed.
- Keep policy/default settings centralized. Printed custom rule values belong to typed definitions/profile data.

## Acceptance evidence

Before implementation: confirm the 24-card source inventory, list discrepancies against current JSON and classify each mechanic as generic reuse, registered extension or unsupported dependency. After separate authorization: each rule has positive/negative engine scenarios, simultaneous/replacement/choice coverage where relevant, actual-server completion, and explicit profile isolation. Changing the selected profile must not leave custom behavior active in ordinary MTG rooms.

The acceptance gate remains open until every confirmed requirement has mapped evidence; the presence of generic discard or usage-limit infrastructure does not establish a specific custom card's support.

## Stop conditions

Stop if source text is missing/contradictory, thresholds would be guessed, Scorch must be patched into universal SBAs, chain state would be tracked by card-specific flags, or implementation requires catalog-ID comparisons. Resolve semantics and extension contracts before code.
