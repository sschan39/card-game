# 4.4 — Event conditions, delayed triggers and turn history

Status: implemented supported declarative conditions, optional choices, delayed lifetimes and per-turn uses. Inspected at `8715503`, 12 October 2026. [Development index](README.md).

## Purpose and structure

Resolve against the recorded triggering event and track meaningful rule history without ad hoc card flags.

| Module | Owns |
|---|---|
| `src/types/rule.types.ts` | Literal/path values and comparison/all/any/not conditions |
| `src/engine/rule-conditions.ts` | Safe own-field path reading and source/controller/event/history context |
| `src/engine/effect-resolver.ts` | Dynamic event values and resolution-time intervening checks |
| `src/engine/turn-history.ts` | Actual event counts/player counts and UUID/revision/ability use keys |
| `src/types/trigger.types.ts` | Delayed registration and current-turn history data |
| `src/engine/trigger-manager.ts` | Delayed matching, one-shot consumption and pending-use reservations |
| `src/engine/effect-registry.ts` / `game-reducer.ts` | Generic creation, registration/removal and expiry |

Conditions use recorded event amounts/snapshots, not current cumulative totals. Missing paths do not match; unresolved dynamic parameters skip the instruction with a typed result. Intervening conditions check at discovery and again at resolution. Optional effects reuse resolution choices.

## Flow

```text
Committed event → chronological history and condition context
 → matching ordinary/delayed trigger + use reservation
 → checkpoint scheduling → optional choice/intervening recheck
 → instructions using recorded event/source information
```

Delayed registrations own controller, source snapshot, definition and lifetime (`once`, `end_of_turn`, `permanent`). They survive source departure; one-shot removal is reserved so repeated events within one batch do not reuse it. Current-turn counts and successful uses persist through room serialization. Actual turn advancement resets history; rejected/cancelled actions consume no use. Earlier events are visible to later events, while simultaneous deaths share their batch's history.

## Extension boundary and remaining work

The [history and scheduling gap record](history-and-scheduling-gaps.md) documents current retention, missing aggregates/capture, game-scoped budgets and relative lifetimes. The [workbook mechanics review](workbook-mechanics-review.md) separates actual card consumers from speculative history/scheduler expansion. These follow-ups are analysis, not implemented extensions.

Extend supported rule values/lifetimes explicitly, keeping data serializable. Current-turn history is not a durable database/replay service. `ActionCondition.globalFlag` in the older action validator is not the implemented declarative trigger-condition system; do not rely on that placeholder for rule-history predicates. New settings remain centralized; authored predicates are rules data.

## Acceptance evidence

`tests/engine/trigger-conditions.test.ts` covers event values, missing data and discovery/resolution conditions. `tests/engine/delayed-history.test.ts` covers lifetime, recovery, source departure, chronological/simultaneous history and use-limit rollback. Actual-server delayed optional trigger and once-per-turn scenarios are in `tests/server/live-routing.test.ts`.

## Stop condition

Stop if a condition needs executable serialized code, a delayed trigger depends on its original source remaining present, or previewed/rejected payment consumes a permanent use record.
