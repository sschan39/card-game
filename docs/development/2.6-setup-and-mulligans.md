# 2.6 — Setup configuration and mulligans

Status: validated centralized setup snapshots implemented; mulligans and deck construction remain open. Inspected at `c651cda`, 12 October 2026. [Development index](README.md).

## Purpose and current structure

Make setup explicit and stable for the lifetime of a room. Keep development decks/profile choices distinguishable from ordinary rules support.

| Module | Owns |
|---|---|
| `src/config.ts` | `SetupConfig`, `gameConfig.setup`, `snapshotSetupConfig` validation/copy |
| `src/engine/room-factory.ts` | Create/join, RPS convention, fixture deck construction and fresh starting-card mutation plans |
| `src/types/game.room.types.ts` | Optional room `setup` and `turnNumber` for legacy compatibility |
| `src/engine/state-machine.ts` | First-turn draw policy and actual turn switch |
| `src/engine/game-reducer.ts` | `SET_TURN` advances turn/history only when requested |

Current defaults: life 20, hand size 4, starting player draws, shuffled nine-card development deck. Validation rejects invalid numbers, booleans, empty/invalid deck IDs and hands larger than the deck; room creation resolves blueprint IDs. The room snapshots defaults before join, so changing global settings does not change that room. Legacy snapshots without setup still use global fallback.

## Flow

```text
Validate/copy setup → create room → join using room settings → RPS starting-player choice
 → build fresh fixture decks/hands → commit setup mutations → ordinary turn entry
```

RPS uses player 1 on a tie and does not increment turn number when selecting the starter. An actual turn switch does increment it. Setup shuffling currently calls `Math.random`; in-game shuffle's injected effect context does not yet make setup replay deterministic.

## Proposed mulligan structure and remaining work

Use an explicit serializable setup stage with per-player decisions, kept separate from priority and stack resolution. Define the selected profile's mulligan procedure before implementation; store decisions and selected exact references rather than callbacks. Existing `choose` transport/ChoicePanel can render decisions, but current continuation types do not include a setup workflow. Start ordinary play only once all setup decisions settle.

Deck validation/selection belongs to 8.5; do not expand named content here. Durable setup replay belongs with 9.3's injected inputs/versioned snapshots. Settings remain in `src/config.ts`; an MTG profile must explicitly override the prototype defaults rather than silently calling four-card hands standard.

## Acceptance evidence

`tests/engine/setup-mana.test.ts` covers setup snapshot stability, invalid defaults, unknown fixture IDs and first-turn drawing. Future gates: both players accept/mulligan independently, repeated choices, exact bottom selections, invalid/stale answers, reconnect before completion, deterministic recorded setup, and no ordinary action before setup ends.

## Stop condition

Stop if mulligans are encoded as normal draw/spell turns, room creation depends on card-specific branches, or joined/recovered rooms silently reread changed defaults.
