# 1.4 — Rules checkpoint

Status: Implemented convergent checkpoint with persisted decisions.

Inspected source baseline: `ad6a96e`, 12 October 2026. [Development index](README.md). Source inspection documents current structure; test paths below identify verification responsibilities, not a new passing run.

## Purpose

Settle atomic changes and state-based actions before scheduling triggers and returning priority.

## Current structure

- `src/engine/rules-checkpoint.ts` — runRulesCheckpoint dependency boundary.
- `src/engine/state-based-actions.ts` — SBA adapter.
- `src/engine/state-based-planner.ts` — simultaneous batches and decisions.
- `src/engine/game-engine.ts` — commit adapters, pending collector and scheduling.

runRulesCheckpoint checks terminal/pending-choice state, applies simultaneous SBAs until stable, drains pending work, schedules triggers, then repeats. An SBA batch that produces no applied progress throws instead of silently looping. Pending decisions suspend further rules work.

## Flow

```text
Atomic commit → repeated SBA batches → pending trigger queue → scheduling decisions → stable checkpoint → priority
```

## Extension boundary

Rule consumers return plans/mutations. They do not recursively call the checkpoint. New decisions use serializable room-owned continuations.

## Remaining work and modification notes

Keep checkpoint order invariant while adding family actions and semantic outcomes. Durable loop policy is 9.1; do not replace convergence with an arbitrary iteration cap.

## Acceptance evidence

- tests/engine/rules-progression.test.ts and tests/engine/state-based-extended.test.ts cover settlement/choices/terminal convergence.
- tests/server/live-routing.test.ts covers actual pending decision reconstruction and client agreement.

## Stop condition

Stop if one mechanic needs triggers scheduled before the relevant SBAs, a recursive checkpoint, or a loop limit that hides unresolved rules work.
