# 8.1 follow-up — Cross-zone casting review

Status: source review complete; implementation scope not approved. Inspected baseline `7abf685`, 12 October 2026. Parent: [zones and library workflows](8.1-zones-and-library.md).

## Current behavior and concrete gap

The checked-in catalog has nine entries. None authors a non-hand casting zone: three explicitly specify hand, and the parser defaults the remaining entries to hand. No current catalog behavior depends on cross-zone casting.

The existing data model nevertheless has `castRequirements.allowedZones: CardZone[]`. `ActionValidator.canActivate` checks the actual card zone against that list. That zone check is not enough to execute a cast from another zone because the surrounding flow is hand-specific.

| Path | Current behavior | Required cross-zone responsibility |
|---|---|---|
| `src/library/card-parser.ts` | Preserves allowed-zone data; defaults to hand | Keep normalized authored requirements |
| `src/engine/action-choices.ts` | Finds cast source only in the acting player's hand | Find a live accessible source and bind its exact zone/revision across prompts |
| `src/engine/handlers/play-card-handler.ts` | Both validation and proposal find only in hand; insertion always moves from hand | Share source/access lookup; move from its actual validated origin |
| `src/shared/action-permissions.ts` | Returns effective prohibition and instant timing, not zone access | Distinguish timing from any future grant of access |
| `src/engine/action-costs.ts` | Reserves hand sources by default; nested mana/discard planning shares reservation | Reserve the chosen cast source throughout payment, independent of origin |
| `src/engine/option-service.ts`, `src/server.ts` | Option requests accept only hand/battlefield | Advertise casting through the same source/access query |
| Existing client option/targeting paths | Zone types and source-name lookups assume hand/battlefield | Reuse current controls with wider source references; no new component |
| `src/engine/zone-transitions.ts` | Atomic validated moves into the spell stack already exist | Reuse the move/reset/stack contract, without a parallel cast handler |

## Example and cause of change

A future generic effect permits casting a specific exiled card. The player has mana and priority. Today `cast_spell` rejects it as "Card not found in hand", before its ordinary modes, targets or payment flow can run. Changing only that lookup still leaves announcement prompts and the final `from: 'hand'` move wrong.

A suspended announcement also needs exact source identity. If the selected card leaves exile and returns with the same UUID, answering the old prompt must not silently cast the returned incarnation or debit costs for an unavailable source.

This is an engine integration gap. It does not justify implementing a named-card handler, moving a card to hand first, or constructing a second payment/stack pipeline.

## Scope choices

1. **Defer until a concrete access consumer — recommended for now.** Current catalog behavior remains complete for its authored source zones. When a consumer arrives, its intrinsic/temporary access rules determine the smallest correct shared contract. Keep this source map so that lookup, choices, payment, movement and options are extended together.
2. **Implement general access now.** First decide what grants access, which exact cards/zones it covers, who may use it, when it expires and how it interacts with the existing allowed-zone requirement. Then implement one shared access/source query and integrate the entire cast flow. This is broader than removing a hand-only lookup.
3. **Refactor hand lookup alone.** Could reduce duplication but would leave the cross-zone behavior unsupported. It is not completion of this roadmap scope and is not proposed as a substitute.

The earlier [8.1 boundary](8.1-zones-and-library.md) and [6.4 permission contract](6.4-characteristic-permissions.md) explicitly distinguish allowed zones/timing from access. Do not silently reinterpret `allowedZones` as an unrestricted casting grant to avoid designing the missing boundary. The owner may simplify that contract, but the decision must be explicit before implementation.

## Acceptance when resumed

- A generic authorized source in another zone casts through the existing command, announcement choices, combined cost plan, atomic stack move and ordinary resolution.
- Options and execution use the same effective source/access query; no hand-move workaround or second cast handler.
- Paused announcement JSON recovery/reconnect retains its selected zone/revision. A departed or returned incarnation fails without paying or replacing the pending request incorrectly.
- The source cannot also be consumed by nested payment selections. Invalid targets/payment/access leave the room unchanged; successful costs and cast events occur once.
- Existing prohibition/timing behavior and target revalidation remain intact. Casting access does not automatically grant visibility, land-play permission, free costs or resolution of a new spell inside a resolving instruction.
- Existing client components/transport are reused. Any missing zone browser remains a separate presentation scope rather than an invented component in engine work.

The tests to extend are `tests/engine/play-card-handler.test.ts`, `tests/engine/action-costs.test.ts`, `tests/engine/pending-choices.test.ts`, `tests/engine/option-service.test.ts`, `tests/engine/characteristic-permissions.test.ts` and `tests/server/live-routing.test.ts`. Source discovery alone is not sufficient acceptance evidence.
