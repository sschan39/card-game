# 8.4 slice — Announced X and concrete numeric consumers

Status: candidate design for owner review; no implementation approval or production changes. Source baseline `66a082a`, inspected 12 October 2026. Parent: [stack breadth](8.4-stack-breadth.md). Source map: [announcement integration review](8.4-announcement-integration-review.md).

## Need and bounded scope

A generic spell costs `{X}{R}`, permits up to X targets and divides X among them. At X=3, its concrete cost is four mana and its announced distribution total is three. Those numbers must agree before any payment, and remain fixed when the spell resolves after mana or board changes.

Today the parser rejects `{X}`; costs, target counts and distribution totals are fixed numbers; choices have no scalar numeric answer; stack objects retain no announced X. Existing modes, target groups, distribution, payment, target revalidation and sequential effects should remain their owners.

This first slice supports ordinary casting and non-mana activated abilities: declared X, mana requirements containing X, top-level numeric effect parameters, target cardinalities and distribution totals. It uses synthetic generic definitions for acceptance and adds no playable catalog card. It does not claim completion of 8.4.

Alternative/additional costs, multiple independent variables, stack copying, X in mana abilities, triggered X selection or inheritance, permanent entry counters and cross-zone casting remain separate contracts. Unsupported uses of the new markers in those definition contexts must fail explicitly rather than silently run with missing values. In particular, an X mana ability must not be reclassified as a normal stack ability to evade its unsupported path.

## Approaches

1. **Small typed expressions plus one derivation boundary — recommended.** Definition values may depend on X; planners and effect handlers receive ordinary numbers. Keeps numeric interpretation out of targeting, payment and effect handlers.
2. **Only substitute X in mana costs.** Smaller, but fails the complete example: targets, effect amounts and divisions would use a different schema. This would be a narrower prerequisite, not this slice's acceptance.
3. **General expression interpreter.** Accommodates arbitrary variables/operations, but brings unnecessary parsing, evaluation and dependency rules. The first slice needs only an integer affine expression.

## Definition and stack data

Add `src/types/announcement.types.ts` with these candidate contracts:

```typescript
interface XDeclaration { min?: number; max?: number }
interface AnnouncementDefinition { x?: XDeclaration }
interface AnnouncementValues { X: number }
type AnnouncedNumber = number | {
  announced: 'X';
  multiply?: number; // default 1
  add?: number;      // default 0
};
interface LockedAnnouncement { values: AnnouncementValues }
```

Declare `announcement` on a card blueprint or non-mana activated ability. X defaults to a minimum of zero. An authored maximum is optional. Bounds must satisfy `0 <= min <= max` when a maximum is present. Declaration bounds, coefficients, offsets and supplied values must be safe integers; the chosen value is nonnegative and within declared bounds. Intermediate multiplication/addition and the final result must remain safe integers. Signed expressions are allowed for effect amounts; mana requirements and cardinalities additionally require nonnegative results. A supplied X for an undeclared action, missing declaration for a marker, extra variable name or malformed marker rejects.

Keep concrete `ActionCost`/`ManaCost` numeric. Introduce authored cost/requirement types that permit `AnnouncedNumber` in the generic mana requirement; colored and colorless requirements remain numeric. Other cost components remain fixed in this slice. Keep resolved requirements numeric for validators. Likewise separate authored target cardinalities/distribution totals from the concrete shapes consumed by target and division planners; do not make those planners accept unresolved expressions.

The shared characteristic facade must carry the announcement declaration with its effective authored requirements/effects. Layer-1 copying replaces that declaration with the donor's, including clearing it when absent. Do not inherit an original blueprint's declaration while copying a different cost/effect schema. Activated-ability declarations travel with the effective ability, including existing ability grants.

Effect parameters remain extensible. Only an explicit top-level parameter value of the reserved `{ announced: 'X', ... }` shape is substituted. Numeric literals and existing `DYNAMIC:` values retain their meanings. Do not evaluate arbitrary handler-owned objects inside `params`. Validation may scan those objects solely to reject reserved X markers in unsupported locations; it must not reinterpret the object's schema. Recurse through typed effect/mode/resolution-branch definitions so a later selected branch also receives the locked announcement's concrete values. A definition trying to put an X expression in an unsupported nested consumer must fail validation rather than be advertised as supported.

`parseManaCost` gains `{X}` in its authored result. Repeated `{X}` symbols and fixed generic symbols combine as one affine generic requirement: `{2}{X}{X}{R}` yields generic `2*X+2` plus one red. Normal numeric-symbol definitions keep their concrete values. A blueprint using `{X}` must declare X; normalization does not infer new gameplay choices from arbitrary rules text.

Accepted stack objects carry optional `announcement: LockedAnnouncement` alongside their concrete effects and target groups. Actions with no declaration need no record. Reconnect and JSON serialization use the existing object/room transport. Resolution consumes concrete parameters and preserves the record; it does not reevaluate X from mana or a source's current characteristics. Future copies may consume the record through their separately designed lifecycle.

## Shared derivation and flow

Create `src/engine/action-announcement.ts` for pure validation and materialization. It accepts a declared announcement, supplied values, authored cost and selected effect definitions. It returns either a clear validation error, a missing-X requirement, or `{ announcement, cost, effects }` with all supported expressions converted to numbers. This function owns expression validation and numeric-domain checks; it does not debit resources, choose targets, allocate identities or mutate room state.

Preparation and execution both call it against the current effective definition. Repeating pure derivation during live revalidation is safe; do not cache the first prompt's interpretation and skip final validation. Mode selection precedes selected-effect derivation; X selection precedes target groups, divisions and payment. Chosen X persists across those prompts.

```text
Live source/timing and effective definition
  → existing mode selection
  → declared X supplied or scalar choice requested
  → shared derivation: concrete mana, effects, counts and totals
  → existing exact target groups and announced distributions
  → existing combined cost/payment planning
  → revalidate source, definition, X, selections and payment
  → atomic costs plus stack insertion with locked X
  → ordinary target revalidation and concrete effect resolution
```

The same derived cost feeds payment prompts and `planActionCosts`; the same effects feed `describeTargetGroups`, `planTargetGroups`, `planAnnouncedDistributions` and stack construction. Invalid definitions/expressions fail before those consumers and before any costs commit. Nested ordinary mana activations continue through their existing shared planner; their definitions remain fixed numeric in this slice.

## Numeric choice and source continuity

Extend `PendingChoice` into a discriminated union preserving the existing listed/allocation branch and adding a scalar `kind: 'number'` branch with a numeric range. The scalar branch does not carry selection-count bounds, option enumeration or an allocation total. Add a distributive draft type for callers constructing choices before IDs/player identity are assigned, so `Omit` does not erase union-specific fields.

Direct cast/activation packets supply `announcementValues: { X: 3 }`; missing X requests a prompt, while a malformed supplied value rejects. Extend the action continuation with `field: 'announcementValues'` and variable identity `'X'` for that prompt. The existing `choose` command accepts `{ choiceId, value: 3 }` only for the numeric branch. Validate a nonnegative safe integer within the range. Existing selections and allocation answers keep their wire shape; mixed or wrong answer formats reject. Narrow the validated scalar answer before updating the action's declared X. The existing ChoicePanel renders one number input with step 1 and the authored bounds, retains cancellation for unpaid action choices, and sends the same command. It must support zero distinctly from blank input.

Action continuations gain a source reference containing UUID, original zone and zone revision, plus ability ID when applicable. Capture it when an announcement first pauses and preserve it through subsequent prompts. On every resumed answer and final submission, require the same live incarnation and effective ownership/ability/timing. Do not refresh the reference to a returned card. An invalid answer or stale source leaves the pending request and resources intact so the player can cancel. New continuations carry the reference; legacy non-X continuations retain their existing compatibility behavior, while an X continuation missing the reference rejects.

Options describe an X action as requiring announcement. They check ordinary timing/source constraints without pretending the unresolved cost is concrete or making a complete affordability claim. After X is chosen, the ordinary cost planner decides payment, including nested mana activations. No new setting or artificial X cap is needed: safe-integer representation and authored bounds are sufficient. Future actual configuration belongs in `src/config.ts`.

`src/client/targeting.ts` currently starts target collection directly from authored definitions for simple casts/activations. For declared X actions, return no local targeting state and submit the ordinary command so server choices establish X before collecting targets. The existing CardComponent/ContextMenu fallback already submits the command when no targeting state is returned. Apply the same rule to any helper exposing unresolved target schemas; fixed-definition targeting retains its current flow. This is a shared declaration check, not a card-specific branch.

## Zero and target behavior

For X=0, an authored `minTargets: 0`, `maxTargets: X` group can choose no targets. With a distribution total of zero, it must complete without an impossible allocation request or nonzero effect mutation. A definition demanding one target and at least one assigned amount cannot complete at X=0; reject without payment instead of clamping X or inventing an allocation.

Target-only legality remains in existing modules. Counts are resolved before group description; stored target references keep their exact revisions. Amounts already divided at announcement remain fixed per target. Later illegal targets do not cause redistribution. The separate targeting review is not part of this slice.

## Stop boundaries

Stop before named-card code, expression evaluation in individual effect handlers, arbitrary scripts, hidden client-only announcement state, definition mutation, invented physical source cards, a payment or targeting bypass, or a new client component. If X requires a new unsupported effect consumer, scope that consumer explicitly before adding it. No implementation starts until the owner reviews this design.
