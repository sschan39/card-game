# 9.1 — Extra/skip turn scheduling and loops

Status: open; ordinary live progression and generic damage passes are foundations. Inspected at `60e9349`, 12 October 2026. [Development index](README.md).

## Current structure and gap

`src/types/game.state.types.ts` supplies a fixed `TURN_SEQUENCE`. `src/engine/state-machine.ts` plans one successor and switches to the other of two players. `src/engine/game-engine.ts` commits/checkpoints one step at a time, with a bounded ordinary automatic chain. `src/engine/combat-rules.ts` extends damage passes within combat; it is not an extra-combat/turn scheduler. `attackedThisTurn` in declaration validation currently blocks another attack that turn.

## Proposed boundaries

| Unit | Responsibility |
|---|---|
| Serializable schedule/cursor | Current turn/step identity, extra/skip instructions and return position |
| Pure next-step planner | Interpret live schedule after current rules settle |
| Entry/reset policy | Per-turn versus per-combat state, skipped-entry behavior and mana lifetime |
| Triggered step creation | Schedule additions through ordinary typed effects/actual commits |
| Loop/choice handling | Identify supported repeat proposals and explicit optional/mandatory decisions |
| Capability/scenario record | Declare supported extensions and keyword consumers separately |

## Proposed flow

```text
Typed schedule change → commit schedule data → finish current checkpoint
 → plan one live successor → entry actions/choices → reread schedule
```

A repeated state alone cannot distinguish a mandatory game loop from player decisions. Define supported loop detection/termination semantics before implementing it. Current applied-replacement IDs prevent a rule reapplying to its own event; they do not solve arbitrary gameplay loops.

## Extension boundary and remaining work

Keep the one-step director and source/choice identity. Define exact insertion/skip precedence, duration and per-combat resets. New keyword consumers remain separately deferred by the owner. A feature manifest should link rule operations to scenarios; registered keys alone do not establish fidelity. Profile defaults belong centrally; do not bury extra-turn limits in handlers.

## Acceptance required

Extra turns chained by both players, skipped turns/steps, extra combats with valid attack resets, triggers adding steps, changes during responses, serialized cursor restoration, optional-loop choices and mandatory-loop outcomes need engine and actual-server transcripts. Existing `tests/engine/ordinary-turn.test.ts` and `tests/engine/rules-progression.test.ts` prove only the foundation.

## Stop condition

Stop if an extension needs a precomputed whole-turn chain, a fixed iteration cap is presented as a game-rule loop solution, or extra combat silently resets all turn history.
