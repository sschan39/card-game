# Setup configuration and mana

Owner scope: setup config, mana payment and mana abilities only. Continue in the existing branch and commit at completion.

Setup: central gameConfig.setup defines starting life, opening hand size, first player's first-turn draw, development deck card IDs and shuffle. Preserve current defaults (20 life, four-card opening hand, first player draws, existing nine-card shuffled fixture deck). Copy settings into each room, so join/reconnect and later turns use the same rules. Track turn number through actual turn switches; choosing an RPS winner does not advance it. Validate settings before creating a room. No mulligans, deck-construction subsystem, land rules, cleanup choices or mana draining changes.

Payment: keep six actual pool colors; add generic to ManaCost and introduce concrete ManaPayment. Parse numeric symbols as generic and C as explicit colorless. A pure payment planner reserves colored/colorless requirements first, then pays generic deterministically from the remaining pool (colorless, white, blue, black, red, green). An optional payment allocation must use known pool colors, nonnegative safe integers, exactly the required total and cover every specific requirement. Validate before committing costs; SPEND_MANA carries concrete allocation only. Unknown mana symbols fail explicitly rather than being silently dropped. X/hybrid/alternate costs remain unsupported in this slice.

Mana abilities: eligibility requires an activated ADD_MANA effect that does not target and is not a loyalty ability. Use abilityIndex to select among multiple mana abilities without overhauling ordinary activated ability identities. No index is accepted only when one eligible ability exists. Land fallback only applies to lands with no defined abilities. Honor selected tap/mana/life costs; non-tap abilities work while tapped or summoning sick. Reject unsupported discard/sacrifice costs rather than granting free output. Require normal priority and timing. Output has one color or a colors list plus amount; multiple colors require a valid manaColor choice. Resolve costs and output atomically without stack insertion. Existing checkpoints handle resulting triggers.

Options: enumerate each eligible mana ability/output choice with action data, and forward that data through the existing context menu. Use the same validation for options and execution. Render generic versus explicit colorless correctly. Default casting remains automatic payment; callers can submit an explicit allocation through the action API.

Validation: generic/colored/colorless payments and forged allocations, failed payment atomicity, multiple abilities/colors, non-tap/sick/tapped sources, unsupported costs/targeted/loyalty eligibility, option-to-command parity, setup snapshots/first-draw tracking, client deltas/reconnect and JSONL. Full suite/typechecks/build/review, then commit.
