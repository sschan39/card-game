# Milestone 3 design

Implement the six items in the existing roadmap in order. The user has authorized reaching the milestone. Preserve the lean debug controls, persistent card identity, pure mutation proposals, centralized configuration, and extensible event logging.

1. **Ability activation:** authored IDs identify activated abilities within a blueprint; the server selects the definition rather than accepting client-supplied costs/effects. A generic `activate_ability` command validates ownership, timing, costs and targets, then atomically pays costs and pushes an activated stack object. Mana abilities retain their immediate route. Hellkite's self buff refers to its source permanent, whereas existing self effects refer to their controller. Normalized blueprint IDs must be unique. Initially unsupported costs are rejected explicitly, then implemented in item 2.
2. **Action transactions:** share cost planning between casting and activation. Explicit discard selections, source sacrifice, tap/untap, mana and life produce one complete mutation batch. Validate selections and interactions before commitment. Costs remain paid after countering.
3. **Targets:** explicit groups identify each targeting clause; all groups use the same legality service during announcement and resolution. Nontargeted self/all selections remain distinct. Preserve a flat-target adapter for existing clients while updating client selection to traverse groups.
4. **Resolution:** determine legal chosen targets and whole-object failure once before effects or structural destinations. A completely failed object executes no effects; partially legal objects execute against surviving targets. Effects still observe preceding mutations.
5. **Choices:** room state owns serializable requests and continuation data. Choice submissions are owner-bound and validated; outstanding resolution choices block ordinary actions. Snapshot/delta restoration must reproduce the prompt. Choice kinds support modes, optional effects, searches, target groups, allocation and ordering with concrete consumers and tests.
6. **Countering and source information:** counter primitives remove a selected stack object immediately, moving only spell cards to their owner's graveyard. Instant fixtures and client stack selection exercise the real server. Abilities resolve independently of source presence, querying live source data while present and last-known information after departure.

Verify each item through meaningful engine and client/server scenarios; commit each completed item. Final audit must cover every roadmap gate, including Hellkite from UI and sockets, duplicate effect abilities, rejected/payment persistence, changed target legality, partial versus total failure, reconnectable choices and source departure.
